## RAG 相关

> 逻辑主线：解释外部知识如何经过索引、检索、证据装配、受约束生成和评测进入模型的一次回答，并在理解机制后判断何时值得建设这条链路
>
> 示例：围绕“查询公司报销制度”，追踪外部资料如何依次变成知识块、候选证据、有效证据和可验证回答

### 一、RAG 首先解决的是外部事实如何进入回答

#### 1.1、模型无法天然知道私有信息

假设用户问：

> 在北京出差，住宿一晚最多能报销多少

即使模型理解“住宿”、“报销”和“北京”，它也未必见过这家公司的最新制度

直接要求模型回答，会同时面对三个问题：

- **知识边界**：模型训练数据，不包含企业内部制度或刚刚更新的资料
- **时效边界**：模型见过旧制度，也不代表旧制度仍然有效
- **证据边界**：模型给出一个数字，不代表这个数字能回到真实条款

==**RAG（Retrieval-Augmented Generation，检索增强生成）** 的核心做法是：回答前先从指定资料中寻找证据，再把问题和证据一起交给模型==

可以先把它理解成一次“开卷回答”，其中存在明确分工：

- 模型负责理解问题和组织语言
- 本轮检索到的资料负责提供事实依据
  - 不是要求模型仅凭参数记忆作答

```text
闭卷回答：问题 → LLM → 答案

检索增强：问题 → 检索证据 → 问题 + 证据 → LLM → 答案
```

> **==RAG 不把知识写进模型参数，而是在调用模型之前为当前问题装配证据==**

#### 1.2、RAG 是一条证据供应链

一条完整链路至少包含：

- 知识资产准备
  - 将原始资料处理成可独立理解的知识块
  - 为知识块建立关键词或向量索引
- 候选证据形成
  - 根据用户问题召回候选证据
  - 过滤、合并并重排候选证据
- 回答生成与校验
  - 把最终证据装配进模型上下文
  - 约束模型基于证据回答并标注出处
- 分层评测
  - 分别评测检索和生成
  - 定位失败发生在哪一层

任何一层失真，都可能让最终答案失真

- 原始资料错误，检索只会更快地找到错误
- 切块破坏语义，相关条款可能永远无法完整召回
- 检索漏掉正确资料，模型没有依据可用
- 上下文混入噪声，模型可能被不相关内容带偏
- 引用只有编号没有语义校验，答案仍可能“答非所引”

==因此，**RAG** 降低的是无依据生成的概率，不是从机制上消灭幻觉==

要让这条证据供应链真正运行，需要先解决**资料**如何提前变得**可检索**，再解决如何**找到并使用**资料

#### 1.3、先记住对象如何逐层变化

完整骨架链路：

```text
基础主链：
原始资料
→ [解析与切片] Chunk
→ [Embedding] 向量
→ [向量索引与向量库] 索引记录
→ [混合召回与重排] 候选证据
→ [证据装配与引用] 有效 Context 与引用
→ 能够回源校验的回答

质量反馈：
回答与各阶段中间结果
→ [分层评测] 可归因的失败结果
→ 反馈到切片、召回、排序或生成环节

边界扩展：
固定链路无法处理的控制或关系问题
→ [Agentic RAG 与图检索] 多轮检索轨迹或关系路径
→ 回到候选证据与 Context
```

每一层都有一个必须回答的问题：

| 骨架节点 | 要解决的问题 | 产生的对象 |
|---|---|---|
| 解析与切片 | 原始文档怎样变成可检索、可引用的最小事实单元 | **Chunk** |
| **Embedding** | 字面不同但意思相近的文本怎样参与同一种比较 | 向量 |
| 向量索引与向量库 | 海量向量怎样快速查询、过滤、更新并映射回原文 | 索引记录 |
| 混合召回与重排 | 怎样兼顾精确字符、语义表达和最终排序 | 候选证据 |
| 证据装配与引用 | 怎样让模型只使用当前证据，并让结论能够回源 | 有效 **Context** 与引用 |
| 分层评测 | 答错时怎样判断是没找到、排错了，还是没有忠实使用 | 可归因的失败结果 |
| **Agentic RAG** 与图检索 | 固定单轮语义检索无法处理的控制与关系问题怎么办 | 多轮检索轨迹或关系路径 |

这张表就是全文的认知地图：前六个节点构成固定 **RAG** 的基础闭环，最后一个节点只在固定链路暴露边界时扩展

### 二、先建立完整运行链：离线建库与在线问答

#### 2.1、同一套 RAG 实际包含两个阶段

用户提问发生在某一刻，但资料不能等到这一刻才开始处理

一套 **RAG** 因此分成两条时间不同、对象相接的链路

- **离线建库** 负责预先把资料变成可检索资产：

```text
原始文档
→ 解析与清洗
→ 切分知识块（Chunk）
→ 生成 Embedding（将文本转换为向量，第三章展开）
→ 写入向量、正文引用及元数据
```

- **在线问答** 负责在问题到来后找到并使用证据：

```text
用户问题
→ 查询理解或改写
→ 召回候选知识块
→ 过滤与重排
→ 装配证据上下文（Context）
→ 基于证据生成
→ 引用与结果校验
```

==**“切块—检索—增强生成”**== 可以作为离线与在线链路的最小抽象：

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901093956220.png" alt="image-20260901093956220" style="zoom: 50%;" />

其中**“切块”**通常发生在建库阶段，**“检索”**和**“增强生成”**发生在问答阶段

两条链通过同一种检索对象相接：

- 离线阶段产出 **Chunk**
- 在线阶段召回 **Chunk**

后面的**向量**、**索引**和**数据库**都围绕这个对象工作，因此第一步不是选向量库，而是先把原始资料变成合格的**检索单元**

#### 2.2、为什么不能直接检索整篇文档

原始文档面向人阅读，不直接等于可检索知识

假设一份差旅制度有 80 页，用户只问“北京住宿一晚最多报多少”

如果把整份制度作为一个检索对象，会出现三个问题：

- **表示失焦**：一个检索对象要同时概括目录、交通、餐费、住宿和历史修订，无法精确代表其中某条规定
- **上下文浪费**：命中后必须把大量无关内容送给模型，挤占有限的上下文窗口
- **引用失准**：系统只能引用整份文档，难以指出答案究竟来自哪条规定

把文档切得过碎也不成立，例如将下面一句拆成两块：

```text
Chunk A：北京地区住宿费上限为每人每天 500 元
Chunk B：自 2026 年 1 月 1 日起执行
```

检索只命中 `Chunk A` 时，金额失去了生效时间；只命中 `Chunk B` 时，又不知道什么规定开始执行

==因此，切片不是为了把文字切短，而是为了形成**既容易命中**、**又保留完整事实**的证据单元==

#### 2.3、Chunk 的边界由事实完整性决定

一份制度里可能同时包含目录、页眉、表格、多个地区标准和历史修订记录

两种简单处理方式都会产生问题：

- 整篇文档作为一个检索对象
  - 命中后会把大量无关内容送进模型
- 按固定字符数机械切分
  - 可能把地区、金额和生效条件拆开

建库阶段因此要依次处理三个问题：

- **解析：**
  - 从 PDF、网页或办公文档中恢复标题、段落、表格等结构
- **清洗：**
  - 删除重复页眉、导航、乱码和无业务意义的格式噪声
- **切块：**
  - 将内容组织成能够独立检索、独立引用的最小证据单元

以差旅制度中的原句为例：

```text
第三章 住宿费
第十二条 北京地区住宿费上限为每人每天 500 元，自 2026 年 1 月 1 日起执行
```

如果只留下“每人每天 500 元”，金额就失去了地区、费用类型和生效时间

如果把整章所有城市标准放进同一个块，检索北京时又会引入其他城市的金额

因此，**Chunk** 不是任意长度的文本片段，而是能够**保住一个事实及其必要限定条件的检索单元**

实际切片通常同时考虑三类边界：

- **结构边界**：标题、章节、段落、列表项和表格行
- **语义边界**：一条规则、一个论点或一个能够独立回答的问题
- **长度边界**：模型和检索系统能够稳定处理的字符数或 **Token** 数，**Token** 是模型计量文本长度的基本单位

每块约 200～500 字可以帮助建立初始直觉，但这只是起点，不是通用答案

- 块太大，主题混杂、召回不精确
- 块太小，限定条件和上下文容易断裂

相邻块可以保留少量重叠内容，但需要同时看到两面：

- 适量重叠
  - 降低事实恰好落在切分边界上的风险
- 重叠过多
  - 制造重复候选
  - 增加索引成本

最简单的滑动窗口切片，可以把机制写成：

```python
def split_with_overlap(tokens, chunk_size=300, overlap=50):
    chunks = []
    start = 0

    while start < len(tokens):
        end = min(start + chunk_size, len(tokens))
        chunks.append(tokens[start:end])

        if end == len(tokens):
            break

        start = end - overlap

    return chunks
```

`chunk_size` 决定每块最多容纳多少内容，`overlap` 把上一块末尾的一部分带入下一块，从而缓冲边界断裂

这个算法能说明长度与重叠，却看不懂标题、段落和表格结构，因此只能作为基础机制

更稳妥的处理顺序是：

- 首先按标题和语义边界切分
- 然后用长度上限处理过长段落
- 最后通过检索评测调整块大小与重叠比例

#### 2.4、Chunk 不只是文本，还要能回源、过滤和更新

知识块至少要携带稳定标识、正文和可过滤元数据：

```python
chunk = {
    "id": "travel-policy-2026#lodging-beijing",
    "text": "北京地区住宿费上限为每人每天 500 元",
    "metadata": {
        "document_id": "travel-policy-2026",
        "section": "住宿费",
        "region": "北京",
        "effective_date": "2026-01-01",
        "version": "2026-v1",
    },
}
```

- 稳定标识用于引用和更新
- 正文用于匹配与生成
- 元数据用于权限
- 版本和范围过滤

如果只存文本而不存来源、版本和生效范围，系统即使检索到了内容，也无法判断：

- 这条规定来自哪里
- 当前版本是否仍然有效
- 当前用户是否有权查看

文档更新时也不能只追加新向量，完整更新链应当是：

```text
识别发生变化的原文
→ 失效或删除对应旧 Chunk
→ 重新切块并生成 Embedding
→ 更新索引、版本和引用映射
```

否则检索结果可能同时出现新旧两个金额，而模型无法判断哪一个仍然有效

#### 2.5、先用关键词检索跑通最小闭环

理解 **RAG** 不需要一开始就引入向量

检索的本质是：为每个 **Chunk** 计算一个“与问题有多相关”的分数，再取分数最高的 `top-k` 个候选

先用关键词重合度把这条骨架显式跑通：

```python
def keyword_score(chunk, question):
    # 假设 tokenize 已经把中文文本切成词
    question_terms = set(tokenize(question))
    chunk_terms = set(tokenize(chunk["text"]))
    return len(question_terms & chunk_terms)


def retrieve(chunks, question, k=3):
    ranked = sorted(
        chunks,
        key=lambda chunk: keyword_score(chunk, question),
        reverse=True,
    )
    return ranked[:k]
```

得到候选后，将原文片段连同问题一起交给模型：

```python
def answer(question, chunks):
    hits = retrieve(chunks, question)

    context = "\n".join(
        f'[{index}] {chunk["text"]}'
        for index, chunk in enumerate(hits, start=1)
    )

    prompt = f"""只根据下面的资料回答问题，资料中没有就明确说明

【资料】
{context}

【问题】
{question}
"""

    return generate(prompt)
```

这段代码已经包含最小 **RAG** 的三个动作：

- 切好的块成为检索对象
- `retrieve` 找到候选
- `prompt` 把候选增强到模型上下文

它还没有真正解决“资料中没有答案”这一情况：

- 只要知识库非空，`top-k` 就会返回相对最像的候选
- 相对最像不等于足以回答
- 证据是否充分，需要在生成前另行判断

但关键词检索只认识字面重合

资料写“计算机采购额度”，用户问“电脑最多可以买多少钱”，两句话意思接近，却可能因为没有相同关键词而错过

这正是 **Embedding** 要解决的上一层缺陷：==把“字符是否相同”改成“语义是否接近”==

### 三、语义如何变成可查询对象：Embedding 与向量库

#### 3.1、Embedding 不是查词表，而是把整段文本编码成坐标

==关键词检索比较的是字面，**Embedding** 比较的是模型从整段文本中编码出的**语义关系**==

它接收一段文本，输出一串固定长度的数字，也就是向量：

```text
“吃饭能报销多少”  → [0.12, -0.38, 0.74, ...]
“餐费报销上限”    → [0.10, -0.35, 0.71, ...]
```

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901094659605.png" alt="image-20260901094659605" style="zoom: 80%;" />

可以先把 **Embedding** 模型理解成一台“**语义坐标生成器**”：

```text
文本
→ 分解成模型能够处理的 Token
→ 结合上下文计算每个 Token 的表示
→ 汇聚整段文本的信息
→ 输出一个固定维度的稠密向量
```

前面的 `[0.12, -0.38, 0.74, ...]` 只是帮助阅读的示意值：

- 真实向量不是人工编写
- 也不是按业务规则硬编码
- 它由训练完成的 **Embedding 模型**计算得到

> “稠密”表示向量中的大量位置都参与表达语义，不像关键词计数那样由某一维直接对应某一个词
>
> 真实向量通常有数百到数千个维度，但人无法把它解释成“第 137 维是动物，第 268 维是价格”

同一个词进入不同上下文，向量也可能不同：

```text
“苹果发布了新手机”中的“苹果”更接近公司和科技产品
“苹果含有丰富膳食纤维”中的“苹果”更接近水果和食物
```

这说明 **Embedding** 不是简单查词表，也不是给每个词永久分配一个固定编号，而是在编码当前这段文本的整体含义

这个表示仍有明确边界：

- **向量不是原文的压缩包，通常不能从向量可靠还原原文**
- **向量接近表示模型认为语义相关，不表示两段文字事实相同**
- **向量不携带权限、版本和真实性判断，这些约束仍由元数据、原文与业务规则负责**

#### 3.2、向量空间把“语义相似”转成“位置接近”

可以把向量空间想象成一张高维地图，每段文字都是地图上的一个点

语义相近的文本通常聚在相近区域，例如，动物、食物和运动相关文本会形成不同的局部簇

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901101534955.png" alt="image-20260901101534955" style="zoom:50%;" />

这张图只承担降维示意：

- 图中使用二维平面帮助观察
- 真实 **Embedding** 空间通常有数百到数千维
  - 无法直接画出来
  - “邻近点代表相似内容”的检索逻辑不变

以报销制度为例：

```text
用户问题：电脑最多可以买多少钱

候选 A：计算机采购额度为 8000 元
候选 B：办公桌采购额度为 2000 元
候选 C：差旅餐费每天上限为 100 元
```

关键词检索可能因为“电脑”和“计算机”字面不同而漏掉候选 A

**Embedding** 模型会完成两步转换：

- 分别为问题和三个候选生成向量
- 在向量空间中比较相对位置
  - 如果模型识别出“电脑”和“计算机”的语义关系
  - 问题向量就应更靠近候选 A

语义检索因此包含两个对称过程：

```text
离线：Chunk.text → Embedding 模型 → 文档向量 → 写入索引
在线：用户问题  → 同一模型体系   → 查询向量 → 查询邻近文档向量
```

调用真实服务时，代码通常只暴露“输入文本、选择模型、取得向量”这层接口：

```python
document_vectors = embedding_client.embed(
    model=EMBEDDING_MODEL,
    inputs=[chunk["text"] for chunk in chunks],
)

query_vector = embedding_client.embed(
    model=EMBEDDING_MODEL,
    inputs=[question],
)[0]
```

建库与查询消费 **Embedding** 的方式不同：

- 建库阶段
  - 批量生成文档向量
- 查询阶段
  - 只生成当前问题的向量
- 模型服务
  - 负责底层上下文编码
- 索引和检索系统
  - 消费最终数值向量

> ==**向量查询**：就是把问题转换成语义坐标，再找出坐标最接近的资料==
>
> ==资料提前变成坐标，问题临时变成坐标；坐标越接近，意思越相似，系统便召回对应的原文==
>
> ==文档和问题进入同一个语义坐标系，查询就是寻找离问题坐标最近的文档坐标，再取回坐标绑定的原文==
>
> ==“同一模型体系”是关键约束==

------

同一索引中的向量必须满足一组共同约束：

- 文档向量与查询向量处在可比较的空间中
- 两者维度一致
- 部分模型还区分文档前缀与查询前缀
  - 此时必须遵循该模型的编码协议

模型、维度或预处理方式变化后，不能默认新查询向量仍能与旧文档向量比较，通常需要重新生成索引或执行受控迁移

选择 **Embedding** 模型时，至少要验证：

- 是否适配当前语言和专业领域
- **检索任务上的召回质量，而不只是通用相似度演示**
- **向量维度带来的存储与计算成本**
- **批量建库和在线查询的延迟、限额与价格**

#### 3.3、余弦相似度与最近邻完成从坐标到候选的转换

文本已经成为坐标后，检索还需要回答两个问题：两个向量有多像，以及从所有向量中取回哪几个

常见的相似度函数是 **余弦相似度（Cosine Similarity）**，它比较两个向量的方向一致程度

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901102822060.png" alt="image-20260901102822060" style="zoom:90%;" />

图中的平行与垂直关系只用于建立方向直觉：

- 可以用它理解余弦相似度
- 不能据此推导所有真实模型的行为
  - 例如，“重复一句话只会改变向量长度”就不是所有 **Embedding** 模型都保证成立的规律

余弦相似度在数学上的取值范围是 `-1～1`：

- 接近 `1`
  - 方向越一致
- 接近 `0`
  - 方向接近正交
- 接近 `-1`
  - 方向相反

```python
import math


def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))

    if norm_a == 0 or norm_b == 0:
        return 0.0

    return dot / (norm_a * norm_b)
```

下面使用人工构造的二维向量说明计算结果，它们只用于理解几何关系，不是真实模型输出：

```python
question = [1.0, 0.0]
computer_policy = [0.9, 0.1]
meal_policy = [0.0, 1.0]

cosine(question, computer_policy)  # 约 0.994，方向接近
cosine(question, meal_policy)      # 0.0，方向正交
```

真实检索依次完成三个动作：

- 计算查询与候选的相似度
- 按分数从高到低排序
- 返回最靠前的 `k` 个候选

这就是 **最近邻检索（Nearest Neighbor Search）** 与 `top-k`

完整的语义检索骨架是：

```python
# 建库阶段，只为每个 Chunk 生成一次向量
for chunk in chunks:
    chunk["vector"] = embed(chunk["text"])


# 查询阶段，为当前问题生成向量并寻找最近邻
def semantic_retrieve(chunks, question, k=3):
    question_vector = embed(question)
    scored = [
        (cosine(chunk["vector"], question_vector), chunk)
        for chunk in chunks
    ]
    scored.sort(key=lambda item: item[0], reverse=True)
    return [chunk for _, chunk in scored[:k]]
```

向量已经归一化时，点积排序与余弦排序等价；是否需要自行归一化，应遵循所选模型和向量库的协议

`top-k` 仍然只是相对排序，不是正确性证明

即使知识库中没有答案，系统也可能返回“最像的三块”；第一名可能只是所有错误候选中最不错误的一条

因此，==**Embedding** 与**相似度**负责产生**候选**，**不能**独自**判断**资料是否真实、有效或足以回答问题==

#### 3.4、向量库解决规模、持久化与过滤

前面的 `semantic_retrieve` 会把查询向量与所有文档向量逐条比较

```text
10 个 Chunk：每次查询比较 10 次
100 万个 Chunk：每次查询最多比较 100 万次
```

数据量增大后，系统还要解决**向量持久化**、**增删改**、**正文映射**和**条件过滤**，单纯在内存列表里逐条算余弦不再够用

这里需要区分两个责任：

- **Embedding** 决定文本怎样成为语义坐标
- **向量库 **决定这些坐标怎样被保存、组织和查询

==**向量库** 不会让一个质量很差的向量突然理解语义，它解决的是“已经有了向量以后，怎样在工程上管得住、找得快”==

**向量库（Vector Database）** 将这些面向检索的责任集中起来：

- `add`：保存向量、稳定 ID、正文引用和元数据
- `query`：根据查询向量返回相近的 `top-k` 候选
- `filter`：只在指定租户、资料类型、版本或时间范围内查询
- `update/delete`：在原文变化后同步维护派生索引

面向向量检索的系统与只做常规字段查询的数据库相比，关键不只是“多存了一列数组”，还在于能够为高维向量建立近邻索引

真实系统常用 **ANN（Approximate Nearest Neighbor，近似最近邻）** 索引缩小比较范围：

- **ANN** 是目标
  - 避免对全部向量做精确穷举
- **HNSW** 是一种常见实现
  - 将向量组织成可快速导航的多层邻接图

查询不再穷举所有向量，而是沿索引优先探索更可能接近查询的位置，用极小的召回损失换取显著的速度提升

可以把这个变化理解成：

```text
精确最近邻：逐个比较所有向量，结果精确，成本随数据量线性增长

近似最近邻：先借助索引进入可能相关的局部区域，再搜索附近向量
```

以 **HNSW** 为例，高层图负责快速跨越较远区域，低层图负责在局部邻居中逐步逼近结果

它返回的是高概率接近的候选，而不是数学上保证穷举后的绝对最近结果，因此需要同时观察：

- 检索质量
  - 召回率
  - 漏召回风险
- 运行成本
  - 查询延迟
  - 内存占用
  - 建索引成本

索引参数越激进，查询可能越快，成本或漏召回风险也可能越高

参数应通过真实问题集校准，不能只看数据库宣称的速度

#### 3.5、从 add 到 query，向量库保存了哪些对象

从接口层看，向量库最重要的动作可以先归纳为“存、查、筛”：

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901105136933.png" alt="image-20260901105136933" style="zoom:80%;" />

这张图把主干压缩成了三个动作；真实工程还必须补上更新、删除、权限隔离和原文回链

先用一个暴力遍历的迷你实现看清接口和数据结构：

```python
class MiniVectorStore:
    def __init__(self):
        self.items = []

    def add(self, id, vector, text, metadata=None):
        self.items.append({
            "id": id,
            "vector": vector,
            "text": text,
            "metadata": metadata or {},
        })

    def query(self, vector, k=3, where=None):
        pool = self.items

        if where:
            pool = [
                item for item in pool
                if all(
                    item["metadata"].get(key) == value
                    for key, value in where.items()
                )
            ]

        scored = [
            (cosine(item["vector"], vector), item)
            for item in pool
        ]
        scored.sort(key=lambda pair: pair[0], reverse=True)
        return [item for _, item in scored[:k]]
```

建库时，系统把已经切好的知识块逐条写入：

```python
for chunk in chunks:
    store.add(
        id=chunk["id"],
        vector=embed(chunk["text"]),
        text=chunk["text"],
        metadata=chunk["metadata"],
    )
```

查询时，只对问题生成新向量，再从允许使用的范围中取回候选：

```python
hits = store.query(
    vector=embed("北京住宿能报多少"),
    k=3,
    where={"region": "北京", "version": "2026-v1"},
)
```

这个迷你实现仍然逐条计算余弦，只用于说明原理；生产向量库在相同接口背后增加持久化、并发控制和近似近邻索引

#### 3.6、向量库是检索索引，不是事实来源

==**向量相似度**只能判断内容是否相关，不能判断内容是否属于当前地区、版本、租户或权限范围==

同一个知识库中也可能同时存在：

- 北京 2025 年住宿标准：每人每天 450 元
- 北京 2026 年住宿标准：每人每天 500 元
- 上海 2026 年住宿标准：每人每天 600 元

它们与“北京出差住宿一晚最多能报销多少”都高度相似，但只有一条同时满足地区和版本约束

==**相似度**负责寻找相关内容，**元数据**负责排除当前任务不允许使用的内容，两者不能相互替代==

正确顺序是先形成允许查询的候选范围，再在范围内进行语义检索：

```text
用户身份与任务范围
→ 形成 metadata filter
→ 在合法分区内做相似度召回
→ 返回候选证据
```

- **过滤与权限**
  - 过滤条件既是检索条件，也是安全边界的一部分
  - 在多租户系统中，不能先跨租户做相似度查询，再从返回结果中删除越权资料
  - 权限范围必须在召回前生效
- **来源与更新**
  - 向量库保存的是由原文派生出的检索对象，原始制度文档才是事实来源
  - 原文更新后，需要让旧 **Chunk** 失效，重新切片、生成向量并更新引用映射
  - 旧向量仍然存在，不代表旧规定仍然有效
- **规模与性能**
  - 数据规模继续增长后，可以用 **向量量化（Vector Quantization）** 降低存储和计算成本
  - 量化可能损失部分召回精度
  - 索引与量化只解决“如何更快找到候选”，不会修复切片断裂、版本过期、权限越界或原始资料错误

到这一步，已经能够保证在合法范围内完成语义召回，但“能够召回”还不等于“召回得准”

下一步的动作是，先校正查询表达，再处理关键词、语义和排序之间的互补

### 四、基础语义召回为何不够：校正输入、扩大召回、压缩噪声

经过元数据过滤，检索已经被限制在合法范围内，但仍可能因为输入含糊或检索路径单一而漏掉正确证据

完整的检索链要依次处理四个问题：

- **查询改写**
  - 把用户意图变成可检索输入
- **互补召回**
  - 用关键词与语义路径扩大候选
- **候选重排**
  - 把真正相关的证据推到前面
- **上下文扩展**
  - 补回生成所需的完整语境

#### 4.1、查询改写先把用户意图变成检索输入

用户输入往往是省略、口语或带有上下文指代的：

```text
“那个能报多少”
```

结合会话上下文后，可以改写成：

```text
“北京地区差旅住宿费的每人每日上限是多少”
```

**查询改写**可以补全对象、范围和关系，也可以把复合问题拆成多个子查询

但改写不是自由创作，不能加入用户没有表达的地区、时间或业务约束

工程上应**同时保留原问题和改写结果**，便于定位召回偏差究竟来自用户输入还是改写器

#### 4.2、关键词与语义检索解决不同问题

报销问题既包含“住宿费上限”这样的语义，也可能包含城市名、制度编号、岗位级别等必须精确命中的字符

只用关键词会漏掉同义表达，只用向量又可能把语义相近但限定条件不同的条款排在前面

关键词检索擅长精确字符串：

- 产品型号 `SKU-8821`
- 人名、法规编号和接口名称
- 必须逐字匹配的专业术语

语义检索擅长表达变化：

- “饭钱”与“餐费”
- “能住多少钱的酒店”与“住宿费上限”
- “离职要提前多久说”与“离职通知期”

最容易记住的分工是：**关键词看字，向量看意思**

前者保住不能模糊处理的实体和编号，后者接住同义词、口语和改写表达

生产系统中的关键词检索通常不会逐篇扫描文本，而是预先建立**倒排索引（Inverted Index）**：

- 索引方向
  - 由词找到包含它的文档
- 查询阶段
  - 先取得相关文档集合
  - 再在较小范围内计算相关性

常见的 **BM25** 会综合三类信号：

- 词在当前文档中的出现情况
- 词在整个资料库中的稀有程度
- 当前文档的长度

罕见且有区分度的词通常会获得更高权重

因此，两条检索路径也常被称为：

- 稀疏检索：围绕离散词项与倒排索引工作，适合精确字符
- 稠密检索：围绕 **Embedding** 向量与近邻索引工作，适合语义关系

**混合检索** 同时使用两路结果，让关键词负责精确命中，让向量负责语义召回

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901105127555.png" alt="image-20260901105127555" style="zoom:50%;" />

如果采用加权分数，必须先校准或归一化两路分数，否则不同量纲不能直接相加

另一种不依赖分数量纲的做法是按排名进行融合，例如 **RRF（Reciprocal Rank Fusion）**：

```python
def rrf(rankings, offset=60):
    scores = {}

    for ranking in rankings:
        for rank, chunk_id in enumerate(ranking, start=1):
            scores[chunk_id] = scores.get(chunk_id, 0) + 1 / (offset + rank)

    return [
        chunk_id
        for chunk_id, _ in sorted(
            scores.items(),
            key=lambda item: item[1],
            reverse=True,
        )
    ]


fused_ids = rrf([
    keyword_search(question, k=30),
    vector_search(question, k=30),
])
```

**RRF** 不要求关键词分和向量分处在同一数值范围，只利用各自在本路结果中的排名

对“北京出差能住多少钱的酒店”这个问题，两路检索各自保留一种信息：

- 向量检索
  - 把口语表达关联到“住宿费上限”
- 关键词检索
  - 保住“北京”这一精确限定

融合后的候选同时继承两路优势

#### 4.3、召回负责尽量不漏，重排负责把正确证据推到前面

第一阶段从大规模索引中快速取回较多候选，目标是提高召回率

第二阶段用更精细的相关性模型重新排序少量候选，目标是让真正有用的证据进入最终上下文

```text
大规模知识库
→ 快速召回 20～50 个候选：优先不漏
→ 精细重排少量候选：优先排准
→ 取前 3～5 个进入 Context
```

召回模型通常只比较已经生成的向量或关键词统计，速度快，适合扫大范围

重排模型会把“问题 + 单个候选”放在一起重新判断相关性，能够看见更细的对应关系，但计算更重，因此只处理有限候选

例如混合召回可能同时得到“差旅申请流程”“北京交通费标准”“北京住宿费标准”等候选

召回阶段宁可暂时多取一些，也不要过早漏掉答案

重排模型再同时阅读问题和候选文本，把直接回答住宿上限的当前条款推到前面

```python
def retrieve_with_rerank(question, k=5):
    candidate_ids = hybrid_recall(question, k=40)
    candidates = load_chunks(candidate_ids)

    ranked = reranker.rank(
        query=question,
        documents=[chunk["text"] for chunk in candidates],
    )

    return [candidates[item.index] for item in ranked[:k]]
```

不能对整个知识库逐条调用大模型打分，那会把一次查询变成高延迟、高成本的线性扫描

重排只处理召回阶段产生的有限候选

#### 4.4、检索粒度与生成粒度可以不同

小知识块更容易精确匹配，但可能丢失前后语境

大知识块上下文完整，却容易引入噪声并占用更多 **Token**

一种常见折中是：

```text
用小块建立索引和匹配
→ 命中后扩展到相邻窗口或父级章节
→ 将较完整的证据交给模型
```

这类策略常见两种实现：

- **Sentence Window Retrieval（句子窗口检索）**：用单句做精确匹配，命中后补回前后相邻句
- **Auto-merging Retrieval（自动合并检索）**：用较小的子块建立索引，命中多个相邻子块时回收对应父级章节

这使“找得准”和“读得全”不必由同一个块大小同时承担

例如索引块只命中“每人每天 500 元”，系统还要补回必要语境：

- 沿引用关系找到父级内容
- 补回标题“北京地区住宿费”
- 补回制度生效日期
- 将完整证据交给模型

块大小、窗口范围和 `top-k` 都不是通用常量，需要用真实问题集验证

> ==查询改写校正输入，混合召回扩大候选，重排压缩噪声，上下文扩展补足语境==

检索链路解决的是“证据能否被找到并排到前面”，下一步还要回答“模型拿到证据后是否真的照着回答”

### 五、有证据为何仍会答错：回答阶段还需要三道闸

#### 5.1、检索正确不等于回答可信

即使正确条款已经进入上下文，模型仍可能：

- 把甲条款中的金额安到乙条款上
- 使用模型自身知识补充资料没有提供的事实
- 引用不存在的来源编号
- 在没有足够证据时给出确定答案

假设上下文只提供了“北京地区住宿费上限为每人每天 500 元”，模型仍可能生成两部分内容：

- “北京地区住宿费上限为每人每天 500 元”
  - 有证据支持
- “超出部分经主管审批后可以报销”
  - 可能来自模型自身知识
  - 当前资料并未提供证据

把相关资料放进上下文，并不会自动把开放式生成变成确定性执行

可信 **RAG** 至少需要三道控制：

- **==证据充分性检查==**
- **==带引用回答==**
- **==引用校验==**

三道控制不是三个独立功能，而是一条有先后顺序的闸链：

```text
候选证据
→ 证据充分性检查：没有依据就停止
→ 带编号生成：每个事实绑定来源
→ 引用校验：编号存在，并且原文真正支持结论
→ 可信回答或明确拒答
```

==第一道闸决定“能不能答”，第二道闸规定“怎样答”，第三道闸检查“答得是否有据”==

#### 5.2、证据不足时在调用模型前停止

检索系统通常会返回 `top-k`，即使所有结果都不相关，也能凑出若干候选

因此“返回了三条”不能作为证据充分的判断

如果用户改问“纽约出差住宿上限是多少”，系统面对的是：

- 用户问题要求纽约标准
- 知识库只有国内城市标准
- 现有候选不足以支持答案

此时应在生成前停止，而不是根据北京或上海标准推测一个金额

```python
def select_supported_hits(scored_hits, minimum_score):
    return [
        chunk
        for score, chunk in scored_hits
        if score >= minimum_score
    ]


hits = select_supported_hits(scored_hits, minimum_score=calibrated_threshold)

if not hits:
    return "资料中未找到足以回答该问题的信息"
```

`calibrated_threshold` 必须针对当前 **Embedding**、相似度算法、数据集和任务类型，通过评测集校准

脱离这些条件写死 `0.3` 没有稳定含义

在高风险场景中，确定性程序应先拦截明显空结果，不必把“是否应该硬答”完全交给模型

#### 5.3、再给证据稳定编号，让回答引用编号

通过充分性检查后，系统才能把证据交给模型，并为每条证据分配稳定编号：

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901105505638.png" alt="image-20260901105505638" style="zoom:50%;" />

```python
def build_context(hits):
    return "\n".join(
        f'[{index}] {chunk["text"]}'
        for index, chunk in enumerate(hits, start=1)
    )


def answer_with_citations(question, hits):
    context = build_context(hits)

    return generate(
        question=question,
        context=context,
        instruction=(
            "只根据给定资料回答；每个事实后标注来源编号；"
            "只能使用已经提供的编号；证据不足时明确说明"
        ),
    )
```

编号应映射回稳定的 `chunk_id`、文档版本和原文位置，而不是只在这一轮显示 `[1]`

用户点击引用时，系统必须能打开真正支撑结论的原始内容

对于贯穿问题，理想输出不是只有一个金额，而是把结论绑定到当前制度：

```text
北京地区住宿费上限为每人每天 500 元 [1]
```

其中 `[1]` 必须能够回到 2026 年制度的具体条款，而不是指向一段临时拼接文本

#### 5.4、引用校验分为结构合法与语义支持

第一层检查引用编号是否存在：

```python
import re


def invalid_citation_ids(answer, source_count):
    cited = {int(value) for value in re.findall(r"\[(\d+)\]", answer)}
    return sorted(
        citation_id
        for citation_id in cited
        if citation_id < 1 or citation_id > source_count
    )
```

这个检查只能发现“给了 `[1][2]`，模型却引用 `[5]`”

编号存在不代表来源真的支持前面的结论

第二层还要检查：

- 每个事实性主张是否带有引用
- 引用段落是否蕴含或直接支持该主张
- 数字、主体、时间和限定条件是否与原文一致
- 多个来源是否存在冲突

> **==引用能回源，结论能被来源支撑==**

三道闸建立了回答阶段的控制机制，但它们是否有效，不能靠几次手工提问判断

这正是下一章分层评测要解决的问题

### 六、系统答错时，先判断证据链断在哪里

#### 6.1、检索和生成必须分开评

只看最终答案，会把两种故障混在一起：

- 正确证据没有被召回
- 正确证据已经召回，但模型没有忠实使用

仍以北京住宿问题为例，如果正确条款没有进入候选，继续修改提示词没有意义

如果正确条款已经排在第一位，答案却写成 600 元，继续更换向量模型也解决不了问题

评测的首要价值不是给系统一个总分，而是确定故障属于知识资产、检索排序、上下文装配还是生成校验

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901105631127.png" alt="image-20260901105631127" style="zoom:50%;" />

检索问题和生成问题的修复路径不同：

```text
检索失败
→ 检查 Chunk、Embedding、过滤条件、混合召回与重排

生成失败
→ 检查 Context 装配、提示约束、模型能力与引用验证
```

#### 6.2、基准评测集是改进的起点

每个样本至少包含：

```python
evaluation_case = {
    "question": "北京出差住宿一晚最多报销多少",
    "gold_chunk_ids": ["travel-policy-2026#lodging-beijing"],
    "reference_answer": "每人每天不超过 500 元",
    "should_retrieve": True,
}
```

同一批问题必须在每次修改前后重复运行，才能判断不同改动带来的是提升还是回退，例如：

- 更换模型
- 调整 `top-k`
- 修改切块策略
- 加入重排

评测集需要覆盖：

- 高频正常问题
- 同义表达和口语输入
- 精确编号、人名与产品型号
- 资料中不存在答案的问题
- 需要多个证据联合回答的问题
- 容易混淆版本、地区和主体的问题

#### 6.3、检索评测先看是否命中，再看排名

**Hit Rate** 衡量正确证据是否进入 `top-k`

**MRR（Mean Reciprocal Rank）** 衡量第一条正确证据排得是否足够靠前

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901105656021.png" alt="image-20260901105656021" style="zoom:50%;" />

```python
def hit_at_k(retrieved_ids, gold_ids):
    return int(any(chunk_id in gold_ids for chunk_id in retrieved_ids))


def reciprocal_rank(retrieved_ids, gold_ids):
    for rank, chunk_id in enumerate(retrieved_ids, start=1):
        if chunk_id in gold_ids:
            return 1 / rank
    return 0.0
```

`reciprocal_rank()` 计算单个问题的倒数排名，对整套评测问题求平均才得到 **MRR**

只看命中率可能掩盖排序问题：正确证据虽然在第八名，但系统最终只把前三名交给模型，实际效果仍等同于没有找到

如果一个问题需要多个证据，单一 `gold_id` 和命中率不够，还要使用覆盖率、召回率等能够反映多证据完整性的指标

#### 6.4、生成评测检查资料相关性、事实忠实度与回答有效性

生成结果至少需要回答三个问题：

- 上下文相关性：送进模型的资料是否真的与问题相关
- 事实忠实度（Groundedness）：答案中的事实能否在资料中找到依据
- 答案有效性：答案是否真正回应了用户的问题

可以由人工标注、规则检查或模型裁判协同评估

模型裁判本身也会漂移，因此重要评测应保留固定提示、固定版本、人工校准样本和可回放输入

#### 6.5、失败归因比总分更重要

| 现象 | 首要检查 | 典型改进方向 |
|---|---|---|
| 正确资料完全没有进入候选 | 建库与召回 | 切块、索引、查询改写、混合召回 |
| 正确资料进入候选但排名很低 | 排序 | 重排模型、特征融合、过滤条件 |
| 正确资料进入上下文但答案编造 | 生成 | 提示约束、模型选择、事实忠实度检查 |
| 回答引用了错误编号 | 输出校验 | 引用结构检查与重试 |
| 编号合法但结论与原文不符 | 语义验证 | 主张拆分、蕴含判断、人工复核 |
| 调整后部分旧问题变差 | 回归 | 固定评测集、版本对比、回滚 |

一个笼统的“RAG 得分 70”无法告诉工程团队下一步该改哪里

有价值的评测结果，会把失败路由到能够负责修复它的环节

到这里，固定 **RAG** 的质量闭环已经完整

接下来要处理三个新问题：是否需要检索、是否需要多轮检索，以及语义相似度是否适合当前问题

### 七、固定检索链何时不够：自主决策与关系遍历

前六章建立的是一条固定证据链：==**每次问题到来，都沿预设步骤完成查询、召回、重排和生成**==

当**知识域明确**、**问题结构稳定时**，这条链通常已经足够；继续增加自主性或新的知识表示，只会带来额外延迟、成本和失败路径

固定链主要在两类问题上暴露边界：

- ==**控制问题**：一次检索无法预先确定要查哪个知识域、拆成几个子问题或是否需要继续补查==
- ==**关系问题**：答案依赖实体之间的明确关系，而不是文本之间的语义相似==

这时就要引入新的技术：

- **Agentic RAG** 处理检索控制，
- 知识图谱检索处理关系遍历，

它们解决的是不同问题，不是固定 **RAG** 的统一“高级版本”

#### 7.1、Agentic RAG 把检索从固定步骤变成工具

固定 **RAG** 对每个问题都执行一次预设检索

**Agentic RAG** 把检索注册为工具，由 **Agent** 根据问题和观察结果决定：

- 是否需要检索
- 应该查询哪个知识域
- 是否要拆分或改写查询
- 当前证据是否足够
- 是否需要再检索一轮

当系统连接多个知识域时，“查哪个库”本身也是一次决策

例如，可以把人事制度、产品手册和历史案例分别注册为检索工具：

```python
search_tools = [
    {
        "name": "search_hr_policy",
        "description": "查询考勤、休假、报销和入离职制度",
    },
    {
        "name": "search_product_docs",
        "description": "查询产品功能、配置、接口和故障排查手册",
    },
    {
        "name": "search_support_cases",
        "description": "查询历史客户问题、处置过程和最终结论",
    },
]
```

工具说明不是装饰文字，而是路由契约

工具说明会直接影响路由：

- 如果三个工具都只写“搜索知识库”
  - 模型缺少选择依据
- 如果说明明确知识域、适用问题和不适用范围
  - “年假还剩几天”可以路由到人事资料
  - “接口返回 429”可以路由到产品手册

一次 **Agentic RAG** 的控制链可以拆成三类判断：

- 路由
  - 是否需要查询
  - 应该查询哪个知识域
- 查询
  - 原问题能否直接用于检索
  - 是否需要改写或拆分
- 充分性
  - 现有证据能否回答
  - 是否需要换查询、换知识库或停止

例如用户问“北京和上海的住宿上限分别是多少，相差多少”，固定单次检索可能只找到其中一个城市

也可能把两个城市的条款混在同一批候选中

**Agent** 可以把任务推进为：

```text
判断需要外部制度
→ 查询北京住宿标准
→ 观察结果并记录 500 元
→ 查询上海住宿标准
→ 观察结果并记录 600 元
→ 计算差额 100 元
→ 证据齐全后停止检索并回答
```

这里新增的能力不是“检索得更准”，而是根据中间结果决定下一步行动

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901110004770.png" alt="image-20260901110004770" style="zoom:50%;" />

```python
import json


MAX_SEARCH_STEPS = 4


def answer_with_agentic_rag(question):
    messages = [{"role": "user", "content": question}]

    for _ in range(MAX_SEARCH_STEPS):
        decision = call_model(messages, tools=[search_kb_tool])
        messages.append(decision)

        if not decision.tool_calls:
            return decision.content

        for call in decision.tool_calls:
            arguments = json.loads(call.function.arguments)
            hits = search_kb(arguments["query"])
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": serialize_hits(hits),
            })

    return "在限定检索轮次内仍未获得足够证据"
```

自主性增加后，需要新增路由准确率、平均检索轮数、延迟、成本和停止原因等评测

单一知识库、问题格式稳定时，固定 **RAG** 往往更便宜、更快、更可预测

只有当问题类型混杂、多知识库路由或多轮补查确实能提升结果时，才值得引入 **Agentic RAG**

#### 7.2、知识图谱检索处理关系链问题

==**向量检索** 擅长寻找意思相近的文本块，却不天然擅长回答 **关系链问题**==

这类问题需要顺着人物、组织或事物之间的关系一层层查找，并把上一步的结果作为下一步的查询起点

例如：

> 张三的经理的邮箱是什么

这个问题需要沿两条关系寻找答案：

```text
张三 --汇报给--> 李四 --邮箱是--> li4@example.com
```

知识图谱把事实表示为“主体—关系—客体”三元组：

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260901110036676.png" alt="image-20260901110036676" style="zoom:50%;" />

```python
triples = [
    ("张三", "汇报给", "李四"),
    ("李四", "邮箱是", "li4@example.com"),
    ("张三", "参与项目", "阿波罗"),
    ("王五", "参与项目", "阿波罗"),
]
```

完整的图检索链并不是直接对原文运行 `neighbors()`，而是先把原始资料变成一致的图结构：

```text
原始资料
→ 识别实体与关系
→ 实体消歧与关系归一化
→ 写入图结构
→ 将问题链接到起始实体
→ 按允许的关系和跳数遍历
→ 将路径及来源装配为回答证据
```

- **向量检索 **的中间对象是相关文本块
- **图检索 **的中间对象是带方向和类型的关系路径

两者最终都要把可回溯证据交给生成模型

最小的一跳邻接查询可以表示为：

```python
def neighbors(entity, triples):
    results = []

    for subject, relation, object_ in triples:
        if subject == entity:
            results.append((relation, object_))
        elif object_ == entity:
            results.append((f"被{relation}", subject))

    return results
```

这段代码只返回一跳邻居

要回答“张三的经理的邮箱”，运行时还要从“李四”继续遍历，并维护遍历状态：

- 已访问实体
  - 防止重复访问
- 当前关系路径
  - 保留回答依据
- 最大跳数
  - 防止无限扩展

实际建图最难的部分不是把文本输出成三元组，而是维护图中的一致性：

- “张三”“张先生”和账号 `zhangsan` 是否是同一个实体
- “汇报给”“直属上级”和“经理是”是否属于同一种关系
- 新旧组织关系冲突时哪一条有效
- 哪个来源有权维护某个实体或关系

如果实体没有消歧、关系没有归一化，图中路径会断裂或错误合并

#### 7.3、向量检索与图检索是互补关系

| 问题形态 | 更适合的入口 | 原因 |
|---|---|---|
| “这份制度主要讲什么” | 向量检索 | 需要开放语义相关内容 |
| “餐费报销上限是多少” | 混合检索 | 同时需要术语和语义命中 |
| “张三经理的邮箱是什么” | 图检索 | 需要沿关系多跳遍历 |
| “比较两个产品的退货政策” | Agentic RAG | 需要拆分问题并多次检索 |

这些检索入口不是彼此排斥的独立方案，可以按问题需要组合：

- **组合方式**
  - 先用向量检索找到语义相关的文本
  - 再根据文本中的实体扩展关系证据
  - 也可以由 **Agent** 根据中间结果动态选择或切换检索入口
- **控制约束**
  - 图检索需要限制跳数、边类型、权限和证据数量
  - 否则一次查询可能遍历过大的关系子图
  - 具体组合没有统一标准，不能因为系统被称为 **GraphRAG**，就默认它遵循同一种架构

==无论检索入口如何组合，召回结果最终都只是 **Context** 的**候选输入**，还需要经过**证据装配**、**生成约束**和**结果校验**==

到这里，前七章已经回答了 **RAG** 如何建立**固定证据链**，以及固定链不足时如何扩展**检索控制**和**知识表示**

但“具备实现能力”不等于“值得采用这套方案”，下一步还要判断当前任务是否真的需要 **RAG**，以及它是否比更简单的证据获取方式更合适

### 八、工程决策：RAG 何时值得使用

前面的固定 **RAG**、**Agentic RAG** 和图检索，已经覆盖了主要检索方式

**RAG** 能解决问题，只能说明这条路线可行

是否值得采用，还要看**有没有更简单的方案**、**额外成本出现在哪里**、**失败后由谁处理**，以及**什么情况下应该停下来**

#### 8.1、外部证据获取方式与 RAG 适用边界

需要外部事实，不等于需要向量库

仍以“北京出差住宿一晚最多能报销多少”为例，资料和问题的形态不同，优先选择的方式也会不同：

| 资料或问题形态 | 优先方式 | 判断依据 |
|---|---|---|
| 当前制度只有几页，能够稳定放进模型窗口 | 直接作为 **Context** | 没有必要额外建设检索索引 |
| 住宿上限已经由报销系统按城市、职级和日期维护 | 调用 **API** 或查询 **SQL** | 业务系统才是当前事实的权威来源 |
| 查询制度编号、城市名、错误码或代码符号 | 全文检索、**BM25** 或 `grep` | 精确字符匹配更加直接 |
| 资料规模很大，用户表达经常与制度原文不同 | 混合 **RAG** | 同时利用精确匹配和语义召回 |
| 需要比较北京、上海和不同职级，并根据中间结果继续补查 | **Agentic Retrieval** | 由 **Agent** 决定查询入口和检索轮次 |
| 问题依赖“员工—职级—城市—适用标准”之间的确定关系 | 结构化查询或图检索 | 显式关系比向量相似度更适合遍历 |

默认选择顺序如下，各种方式在实际系统中也可以组合使用

- 先找能够直接读取权威事实的最窄路径


- 固定检索不够时，再用 **Agent** 动态选择入口或继续补查


==**RAG** 是获取外部证据的一种方式，并不等于接入外部知识本身==

是否选择它，还要比较从资料准备到在线查询的实际成本，并确认版本、权限和失效处理是否可控

#### 8.2、RAG 的全链路成本结构与方案取舍

**RAG** 会增加存储、计算、响应时间和失败路径

直接使用 **Context**、全文检索或 `grep` 同样需要付出成本，只是成本出现在不同环节

| 路线 | 主要前置成本 | 主要运行时成本 | 主要取舍 |
|---|---|---|---|
| 直接 **Context** | 资料整理与上下文模板 | 每次查询都要支付输入 Token 和长上下文延迟 | 省去向量索引；资料过多后容易引入噪声 |
| 全文检索或 `grep` | 文本可访问；全文检索还需倒排索引 | 查询规划、多轮搜索与文件读取 | 精确字符检索直接；同义表达和隐含语义可能漏检 |
| 向量或混合 **RAG** | 解析、切片、Embedding、索引与同步 | 查询向量、召回与重排 | 将成本前置到建库和同步；重复查询时更容易摊薄成本，但切片、召回、排序和版本都可能失真 |
| **Agentic Retrieval** | 工具契约、权限和停止规则 | 多轮推理、工具调用、Token 与延迟 | 使用 `grep` 等工具时可以减少离线建库；查询设计、文件读取和多轮判断被转移到每次运行，轨迹和停止原因更难稳定 |

==**RAG 的决策不是要不要付出成本，而是把成本放在建库、查询、模型还是持续治理的哪一层**==

只说“向量库很贵”或“长上下文更简单”，都不足以决定方案

需要同时观察五个变量：

| 变量 | 对方案选择的影响 |
|---|---|
| 总成本 | 比较从资料准备到在线回答的全部投入，而不是只看向量存储价格 |
| 结果质量 | 判断增加检索机制后，回答质量是否稳定改善 |
| 失败后果 | 判断错误、遗漏或过期证据会造成什么影响 |
| 查询频率 | 查询次数越多，离线索引越容易摊薄成本 |
| 资料变化频率 | 资料变化越快，索引同步和维护的压力越大 |

查询频率决定索引能够被复用多少次，资料变化频率决定索引需要被维护多少次，两者需要放在一起考虑

#### 8.3、生产级 RAG 的技术路线与组件选型

**RAG** 链路的关键节点：

```text
结构化解析与切片
→ 文档向量与关键词索引
→ 元数据和权限过滤
→ 关键词 + 稠密向量混合召回
→ 融合与重排
→ 证据装配、生成、引用与评测
```

每个节点的技术候选：

| 层级 | 成熟候选 | 选择依据 |
|---|---|---|
| 解析与切片 | [**Unstructured**](https://docs.unstructured.io/open-source/core-functionality/chunking)、[**LlamaIndex**](https://docs.llamaindex.ai/en/stable/api_reference/node_parsers/semantic_splitter/)、[**LangChain**](https://docs.langchain.com/oss/python/langchain/retrieval)、[**Haystack**](https://docs.haystack.deepset.ai/docs/creating-pipelines) | 复杂文档选结构化解析；已有框架则复用现有流水线 |
| **Embedding** | 托管模型可选 [**OpenAI** `text-embedding-3` 系列](https://platform.openai.com/docs/guides/embeddings)、[**Voyage 4**](https://docs.voyageai.com/docs/embeddings)；自托管可选 [**Qwen3-Embedding**](https://github.com/QwenLM/Qwen3-Embedding)、[**BGE-M3**](https://github.com/FlagOpen/FlagEmbedding/blob/master/docs/source/bge/bge_m3.rst) | 低运维选托管；数据隔离选自托管；最终以业务检索集验收 |
| 检索与存储 | [**pgvector**](https://github.com/pgvector/pgvector)、[**Elasticsearch**](https://www.elastic.co/docs/solutions/search/hybrid-search)、[**Qdrant**](https://qdrant.tech/documentation/search/hybrid-queries/)、[**Milvus**](https://milvus.io/docs/hybrid_search_with_milvus.md)、[**Weaviate**](https://docs.weaviate.io/weaviate/concepts/search/hybrid-search)、[**Pinecone**](https://docs.pinecone.io/guides/search/hybrid-search) | 优先复用现有基础设施；边界明确后再引入专用向量系统 |
| 重排 | 托管模型可选 [**Voyage** `rerank-2.5`](https://docs.voyageai.com/docs/reranker)、[**Cohere Rerank 4**](https://docs.cohere.com/docs/rerank)；自托管可选 **Qwen3-Reranker**、**BGE Reranker** | 召回生成候选，重排只精排小集合 |
| 流水线编排 | **LlamaIndex**、**LangChain**、**Haystack**，或者应用内部的显式流程 | 只连接组件，不承载权限、版本、评测和容错 |

#### 8.4、“RAG 已死”争议与检索范式演进

“**RAG 已死**” 论调的形成有以下几个原因：

- 生产级 **RAG** 的成本开始暴露
- 长上下文和 **Agent** 工具调用提供了新的取证方式
- **Claude Code** 一类系统又证明 `grep` 和文件读取在代码场景中非常有效

##### 8.4.1、朴素向量 RAG 的生产代价

当前受到质疑的主要是下面这条朴素向量链路：

```text
固定长度切片
→ 单一向量召回
→ Top-K 全部装入 Prompt
→ 模型直接生成
```

它把检索质量押在一条单向链路上：

- 切片丢失的上下文无法由 **Embedding** 恢复
- 召回漏掉的证据不会进入生成阶段
- 候选过多又会稀释模型注意力

演示系统通常使用静态资料、少量样例和人工挑选的问题，因此这些缺陷并不明显

进入生产后，资料会更新和删除，用户具有不同权限，查询分布也会不断变化，索引错误还可能被模型包装成看似可信的回答

为了修补这条链，系统需要增加**结构化切片**、**混合召回**、**查询改写**、**重排**、**引用校验**、**分层评测**、**监控和降级**，原本简单的模型调用也因此变成**需要持续治理的数据与检索系统**

==**最小 RAG 原型并不昂贵，昂贵的是让它在资料持续变化和答案可能出错时仍然保持可信**==

长上下文、**Prompt** 缓存和更强的工具调用能力又提供了可比较的替代路线

##### 8.4.2、RAG 与 Grep 的成本比对

**RAG** 和 **Grep** 在不同阶段的成本：

| 比较维度 | RAG | Grep |
|---|---|---|
| 资料准备 | 预先解析、切片、建索引并持续同步 | 几乎不做派生索引，保留可直接读取的原文 |
| 查询过程 | 一次或少量检索即可产生候选 | 多轮搜索、读取、判断、改写关键词和重试 |
| 主要成本 | 建库、存储、同步与检索服务 | 模型轮次、工具调用、文件读取、Token 与延迟 |
| 资料时效 | 取决于索引是否及时更新 | 直接读取当前文件，天然接近最新状态 |
| 质量风险 | 切片失真、召回遗漏、排序错误和索引过期 | 查询计划错误、搜索范围失控、遗漏路径和停止过早 |
| 可观察性 | 相似度和排序错误需要专门评测与归因 | 搜索词、读取文件和工具轨迹更容易直接检查 |

==**Grep 省掉的是预先建库，不是检索本身；它把索引维护成本换成了每次查询的动态探索成本**==

- 当同一批资料被大量重复查询时，离线索引更容易摊薄成本
- 当资料频繁变化而查询较少时，运行时搜索可能更经济

##### 8.4.3、Claude Code 案例的可外推边界

代码库并不是普通的非结构化文本集合，它天然提供文件路径、目录层级、函数名、类型名、错误码、调用关系和版本历史等**高质量检索锚点**

**Agent** 可以根据中间结果不断调整关键词，读取相邻代码，再通过编译器、类型检查、测试、**AST** 或 **LSP** 验证判断

工作区原文同时又是当前事实，不需要等待派生索引同步

[**Claude Code** 官方实践](https://www.anthropic.com/engineering/claude-code-best-practices) 描述的正是由 **Agent** 自主搜索代码库、沿结果继续探索的工作方式

因此，**Grep** 在代码场景中的成功证明的是：==**当资料已经存在精确锚点、可直接读取并能够逐步验证时，运行时探索可能优于预先向量化**==

==它不能证明法律条款、客服记录、研究报告或大量自然语言资料也具备相同条件==

==这些资料往往存在同义表达、上下文依赖和跨文档证据，仍然需要语义召回、混合检索或重排==

##### 8.4.4、检索范式的分化与职责保留

公开资料也不足以支持“**Anthropic** 已经从 **RAG** 全面转向 **Grep**”的判断

- [**Contextual Retrieval**](https://www.anthropic.com/engineering/contextual-retrieval) 继续使用 **Embedding**、**BM25**、上下文化切片与重排处理大型知识库
- [**Claude Projects**](https://support.anthropic.com/en/articles/11473015-retrieval-augmented-generation-rag-for-projects) 在项目知识接近上下文限制时仍会自动启用 **RAG**
- **Claude Code** 则在**结构明确**、**持续变化**的代码库中采用 **Agent 主导的搜索与读取**

这不是前后矛盾，而是同一职责开始根据数据形态采用不同实现：

```text
固定切片 + 单一向量 Top-K
→ 关键词与向量混合召回
→ 上下文化切片与重排
→ 查询路由与多种检索工具
→ Agent 根据中间结果动态补查
```

是否把 `grep → Read → Context → Generate` 也称为 **RAG**，取决于采用宽泛的职责定义，还是狭义的向量知识库定义

名称并不是关键，关键是三个责任仍然存在：

- 根据问题寻找外部资料
- 选择可以进入本轮 **Context** 的证据
- 约束模型基于证据生成

> **==“RAG 已死”真正否定的是朴素向量 RAG 作为默认选择的地位==**
>
> **==外部取证没有消失，检索正在从固定单链路演进为按数据形态选择、由 Agent 动态编排的多种路线==**

### 九、边界：RAG、Memory 与 Context 各自负责什么

#### 9.1、三者共享检索技术，不共享责任

| 概念 | 主要对象 | 核心责任 | 进入模型前的形态 |
|---|---|---|---|
| **RAG** | 外部知识与证据 | 为当前问题寻找可信资料 | 检索到的证据块 |
| **Memory** | 历史状态、偏好与经验 | 决定什么值得长期保存、召回、更新和遗忘 | 相关记忆条目 |
| **Context** | 当前调用所需的全部输入 | 在预算内组装指令、历史、证据、记忆与工具结果 | 本轮模型输入 |

记忆条目可以使用 **Embedding** 和向量库召回，技术上与 **RAG** 相似

但两者的治理问题不同：

- **RAG** 关注资料来源、版本、访问范围和证据支撑
- **Memory** 关注写入价值、主体归属、冲突更新、时效和遗忘
- **Context Assembly** 决定本轮究竟把哪些信息放进模型窗口

被检索到不等于必须进入上下文，进入上下文也不等于模型一定会正确使用

#### 9.2、最终记忆模型

整篇文章可以收束为一个决策入口和两条相互连接的链：

```text
决策入口
需要外部事实
→ 选择最窄可行的取证方式
→ 确认是否值得建设 RAG

离线知识链
原始资料
→ 解析与切块
→ Embedding 与索引
→ 可查询的知识资产

在线证据链
用户问题
→ 查询理解
→ 召回与过滤
→ 重排与证据装配
→ 基于证据生成
→ 引用与结果校验
→ 分层评测与失败归因
```

一旦决定使用 **RAG**，固定证据链是默认起点，两类扩展只替换其中一部分能力：

- 问题需要动态拆解和多轮补查时，由 **Agentic RAG** 接管检索控制
- 问题依赖明确关系和多跳路径时，由图检索提供关系证据

无论检索由谁控制、证据如何组织，结果都要回到同一条主线：进入 **Context**，约束生成，并接受引用和评测

这条链并不是所有问题的默认基础设施

只有当直接 **Context**、业务接口或精确检索不能经济地提供证据时，才需要承担 **RAG** 的建库和治理成本

其中：

- **Embedding** 表达语义位置
- 向量库提供近邻索引和过滤
- 混合召回负责尽量不漏
- 重排负责把正确证据推到前面
- 生成模型负责基于证据组织回答
- 引用与兜底限制无依据输出
- 评测负责定位改动究竟改善或破坏了哪一环

> **==检索提供证据，生成受证据约束，评测定位证据链断点==**
