## 知识库架构设计方法论

### 一、方法论要解决的问题

知识库路由设计的本质问题是：==**如何把自然语言输入变成可判断、可过滤、可继承、可裁决的结构化条件**==

**用户输入通常是混合语义，不会按知识库标准词表达**

系统要做的不是直接把一句话塞进某个桶，而是拆成多个职责清晰的结构：

```text
自然语言
-> 标准标签
-> 层级主轴
-> 横向条件
-> 实体属性
-> 决策结果
-> 下游消费
```

本文把这套方法统一命名为 **“分面单轴漏斗路由”**，名字对应四个可迁移的部件：

- **分面**是正交维度平铺打标、相交收敛
- **单轴**是层级深度只给一根真正需要继承的轴
- **漏斗**是下钻、回退与硬闸收口
- **路由**是把自然语言最终裁决到有限实体

这套方法可以迁移到其他 **Agent** 知识库、**RAG** 路由、意图树、商品推荐和有限实体决策场景

### 二、关系判断：包含、并列、正交

设计任何知识库轴之前，先判断两个值或两个维度之间是什么关系

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-05-relationship-types.png" alt="diagram-05-relationship-types" style="zoom:25%;" />

三种关系分别是：

| 关系 | 判断方式 | 结构选择 |
| --- | --- | --- |
| 包含 | A 是 B 的一种 | 可以形成层级 |
| 并列 | A 和 B 同属一轴，通常二选一 | 做同轴兄弟 |
| 正交 | A 和 B 可以同时成立 | 做平铺 `facet` |

可复用判据：

**给任何一个知识维度归类前，先问它和已有维度是包含关系还是正交关系**

包含才考虑进树

正交一律平铺打标，靠相交收敛

### 三、原则一：单轴漏斗

单轴漏斗不是说世界上只能有一棵树，而是说主路由的层级深度只给一根最关键的轴

这根轴必须同时满足两个条件：

- 真有 `is-a` 嵌套
- 确实需要 `parent` 回退

如果一个轴只是“看起来可以分层”，但不需要子节点继承父节点默认字段，就不该进入主漏斗

多轴嵌套的问题是组合爆炸

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-04-tree-explosion-vs-facet.png" alt="diagram-04-tree-explosion-vs-facet" style="zoom:25%;" />

一旦把多个正交轴都塞进树：

```text
叶子数 = 场景 × 人群 × 分型 × 阶段 × 部位 × 症状
```

维度越多，树越大，重复越多，维护越不可控

所以更稳的设计是：

```text
一根层级轴负责下钻
多个平铺 facet 负责过滤
实体属性负责裁决
```

### 四、原则二：四类元素分离

知识库里的元素天然职责不同，不能放进同一个结构

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-02-four-elements.png" alt="diagram-02-four-elements" style="zoom:25%;" />

四类元素是：

| 类别 | 作用 | 典型结构 |
| --- | --- | --- |
| 路由主轴 | 定位核心业务场景 | 层级漏斗 |
| 正交 `facet` | 叠加横向约束 | 平铺字段 |
| 实体属性 | 描述可被裁决的对象 | 产品卡、能力卡、禁忌卡 |
| 下游消费 | 决定结果如何表达 | 内容类型、风格、标签、合规 |

这套分离的价值是：每类元素只回答一个问题

- 主轴回答“在哪里”
- `facet` 回答“还满足哪些条件”
- 实体属性回答“能不能承接”
- 下游消费回答“怎么表达”

如果一个自然语言词同时回答多个问题，就应该拆成多个轴上的原子标签，而不是做成一个混合分类值

**混合词要拆轴，单一轴才可组合**

### 五、`facet` 与相交收敛

`facet` 的核心不是“标签越多越好”，而是用多个独立描述轴表达对象

平铺打标是数据侧动作：

```text
给对象和查询填字段
```

相交收敛是查询侧动作：

```text
用多个条件 AND 过滤候选集合
```

关系数据库里的 **WHERE** 条件是最直接的类比：

```sql
WHERE scenario = '术后'
  AND population = '儿童'
  AND body_part = '颈部'
  AND scar_type = '增生'
```

这套结构的优势是组合优于穷举

不用提前写出“儿童 + 术后 + 颈部 + 增生”的所有叶子节点，而是在运行时让条件组合起来

### 六、字段级继承

`parent` 回退是字段级继承，不是整体替换

子节点命中后，仍然保留子节点身份

只有当某些字段缺失时，才向父节点取默认内容

规则是：

- 子节点有值，用子节点
- 子节点缺值，向父节点补
- 子节点明确覆盖，以子节点为准
- 子节点明确排除，不能被父节点重新加回来

这也是为什么只有真正需要继承的轴才适合做层级

**parent 回退（继承）才是层级树存在的核心理由**

### 七、理论来源与边界

这套方法不是新发明，而是把关系数据库、**OLAP** 和 **Facet** 分类里的共通抽象迁移到知识库路由设计中

| 领域 | 既有概念 | 对应的知识库路由概念 |
| --- | --- | --- |
| 关系数据库 | **WHERE** 谓词过滤 | `facet` 相交收敛 |
| **OLAP** | `drill-down` 下钻 | 场景漏斗逐层收窄 |
| **OLAP** | `roll-up` 上卷 | `parent` 字段回退 |
| **OLAP** | 维度建模 | 一根层级轴 + 多个平铺维度 |
| 分面分类 | 多分面正交描述对象 | 平铺 `facet` 打标 |

可复用的不是这些技术栈本身，而是三条结构原则：

- 用独立的轴描述对象
- 用谓词筛选候选集合
- 用层级下钻和回退控制粒度

迁移到知识库路由时要守住边界：`facet` 是查询条件组合，不是新的层级轴；实体裁决是漏斗收口，不是继续无限下钻

### 八、原则三：一图双向

一套好的知识库结构不只支持正向生成，也应该支持反向盘点

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-03-bidirectional-flow.png" alt="diagram-03-bidirectional-flow" style="zoom:25%;" />

正向用于生成决策：

```text
关键词
-> 场景
-> 条件
-> 实体
```

反向用于覆盖盘点：

```text
实体
-> 能力
-> 场景
-> 关键词
```

如果正向和反向各做一套表，就会出现真值漂移

同一个业务事实在不同地方变成不同版本后，系统会出现决策错误、覆盖误判和维护失控

所以一图双向的核心不是“图能倒着看”，而是“同一套结构同时服务生成和治理”

**同一张结构正向用于决策，反向用于盘点；生成和运营不再各维护一套真值**

### 九、从项目到方法的抽象验证

项目图示的价值不是补充更多项目细节，而是验证这套方法能解释真实问题

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-01-flat-vs-funnel.png" alt="diagram-01-flat-vs-funnel" style="zoom:25%;" />

方法论能解释旧结构的问题：

- 平桶路由缺少可继承的层级轴
- 多个正交维度混在一起，导致职责不清
- 实体裁决真值分散，导致漂移
- 下游能生成内容，但不一定稳定对应正确实体

方法论也能解释目标结构的改进：

- 单轴漏斗解决场景纵向下钻
- 平铺 `facet` 解决横向条件组合
- 实体属性和硬闸解决产品裁决
- 一图双向解决生成和覆盖盘点的统一

因此，当前项目只是方法的来源样本，不是方法的适用边界

### 十、适用边界

这套方法适合：

- 决策空间有限
- 实体数量可枚举
- 有明确硬约束
- 需要可解释、可审计、可人工维护
- 至少有一根维度具备稳定的 `is-a` 层级

这套方法不适合直接替代所有语义检索

如果任务是从大量非结构化语料中找相似内容，纯 **Vector Search** 或混合检索更合适

但如果任务是把用户表达路由到有限实体，并且存在安全、合规、人群、禁忌等硬约束，就不能只靠向量相似度

更稳的组合是：**向量 / LLM 负责自然语言归一，符号规则负责约束决策**

### 十一、复用时的不变量与变量

把这套方法带到新项目时，先分清哪些是骨架、哪些是皮肉

不变量，换项目也应保留的核心结构：

- 关系判断先行：包含进树，正交平铺
- 一根层级主轴 + 平铺 `facet` + 实体属性的三分结构
- 字段级 `parent` 回退规则
- 硬约束一票否决先于软条件排序
- 同一套结构正向决策、反向盘点

变量，每个项目都要重新回答的问题：

| 变量 | 要回答的问题 | 举例 |
| --- | --- | --- |
| 业务域 | 层级主轴选哪根轴 | 当前项目是场景，客服系统可能是意图，商品推荐可能是品类 |
| 标签体系 | `facet` 有哪些轴，词表是什么 | 医疗域是人群 / 部位 / 分型，招聘域可能是职级 / 城市 / 技能 |
| 实体属性 | 被裁决的对象是什么，硬闸由什么决定 | 产品、文档、工单或 **API**，硬闸可能来自合规、权限或库存 |
| 下游消费 | 路由结果交给谁 | 内容生成、推荐排序、工单分派 |

复用的正确顺序是先用关系判断重建轴，再填词表，最后接下游；不要把当前项目的词表直接搬进新域

### 十二、总结

分面单轴漏斗路由的可迁移方法论可以压缩成五条：

- 先判断关系：包含进树，正交平铺
- 主漏斗只给一根真正需要继承的轴
- `facet` 用来组合条件，不用来制造嵌套树
- 实体属性和硬闸负责裁决，不和标签混在一起
- 同一张结构正向生成、反向盘点，避免多套真值漂移

最终记忆点：**好的知识库路由设计，不是把所有可能性穷举成树，而是用单轴定位问题，用分面表达条件，用漏斗完成裁决**
