## 未来复杂度演进蓝图

本文回答一个前提问题：当前“分面单轴漏斗路由”是否足以支撑后续业务复杂度，以及未来复杂度上升时应该沿哪些扩展点演进

结论是：当前路由模型足以作为近期业务演进底座，不需要现在就引入完整的多账号系统、SKU 生命周期状态机或运营中台；但目录和文档需要明确保留扩展口，避免未来复杂度只能靠继续扩张 `scenario` 树来承接

## 一、当前模型能支撑什么

当前模型已经解决了内容生产里最关键的结构问题：

```text
自然语言输入
-> 模糊归一
-> scenario 下钻
-> facet 相交
-> parent 回退
-> 人群硬闸
-> SKU 裁决
-> 下游消费
```

这条链路能稳定支撑以下近期需求：

- 新增长尾关键词，只进入 `registry`，不新增第二套路由表
- 新增细分场景，只补 `UseScenario` 节点和 `parent`，不让多轴组合爆炸
- 新增人群、部位、阶段、症状、分型约束，只扩展 `facet` 词表
- 调整产品承接关系，通过 `sku_map`、SKU 卡和硬闸字段完成
- 内容生产、视觉风格、合规规则消费路由结果，不反写主轴

因此当前模型不是临时权宜方案，而是可以继续丰富的底座

## 二、当前模型暂不解决什么

当前模型不应该过早承担三类复杂度：

| 复杂度 | 当前处理 | 暂不做成主架构的原因 |
| --- | --- | --- |
| SKU 生命周期 | 在 SKU 卡中保留 `routable`、`population_gate`、`stage_gate`、`gate_review` 等字段 | 目前 SKU 数量少，未形成频繁上下架和渠道差异 |
| 多账号矩阵 | 作为下游分发和表达层消费路由结果 | 蓝 V 到素人号的差异主要是口吻、人设、转化强度，不是场景主轴 |
| 运营状态机 | 通过人工提拔和 `exemplars` 控制沉淀 | 现阶段不需要把每次产物都做成完整入库审核工作流 |

这三类复杂度都重要，但不应提前压进 `scenario` 或 `facet`，否则会把清晰的路由模型重新变成复杂树

## 三、SKU 生命周期的未来扩展口

SKU 更新、新增、下架是最确定会出现的复杂度

当前应该保留的原则是：

```text
SKU 的生命周期属于 SKU 实体属性
不属于 scenario 主轴
不属于 facet 词表
```

未来 SKU 卡可以自然扩展三类字段：

- 生命周期字段：是否上架、是否废弃、是否有替代品
- 路由资格字段：是否允许进入自动路由，是否需要人工确认
- 渠道与合规字段：是否在当前渠道可售，是否具备必要审批状态

也就是说，未来可以从当前的“人群硬闸”扩展成“资格闸”：

```text
候选 SKU
-> 人群硬闸
-> 阶段硬闸
-> 生命周期硬闸
-> 渠道硬闸
-> 最终裁决
```

这不会推翻当前模型，只是在 SKU 实体层增加更多资格字段

## 四、多账号矩阵的未来扩展口

后续会从蓝 V 号扩展到孕妇素人号、术后疤痕素人号、儿童家长号等账号

这些账号不应该进入 `scenario` 主轴

原因是：

- 孕妇素人号不是一种业务场景，而是一种表达身份和分发策略
- 术后疤痕素人号可以覆盖外科术后、医美术后、烫伤外伤等多个场景
- 同一个 `scenario` 可以被蓝 V 和素人号同时消费，只是内容口吻不同

未来账号卡应属于下游消费层，主要描述四类信息：

- 账号身份：蓝 V、素人号、专家号、店铺号
- 可承接范围：允许消费哪些场景、人群和产品
- 表达策略：口吻、视角、转化强度、内容风格
- 发布边界：合规等级、禁用表达、人工确认要求

它的消费位置应在路由之后：

```text
keyword
-> route_schema 决定 scenario / facets / SKU
-> account profile 决定口吻 / 视角 / 转化强度 / 发布边界
-> production_specs 决定图文结构
-> compliance 做最终审查
```

一句话：账号矩阵改变“怎么说”和“发给谁”，不改变“这个问题属于什么场景、该由什么 SKU 承接”

## 五、未来复杂度的归属规则

为了避免后续所有新概念都被塞进 `scenario`，需要固定一张判断表

| 新复杂度 | 应放位置 | 不应放位置 |
| --- | --- | --- |
| 新业务场景，存在父子包含和字段继承 | `route_schema/scenarios` | `facets` |
| 新人群、部位、阶段、症状、疤痕类型 | `route_schema/facets` | `scenarios` |
| 新 SKU、新成分、上下架、替代关系 | `entities/skus` / SKU 卡字段 | `scenarios` |
| 蓝 V、素人号、专家号、店铺号 | `content_runtime/accounts` | `scenarios` |
| 新图文结构、爆款结构、封面风格 | `content_runtime/production_specs` / `visual_style` | `route_schema` |
| 合规红线、注册证、广审号、审核状态 | `entities` + `governance` | `viral_patterns` |
| 竞品资料、趋势资料、原始样本 | `market` / `assets` / `data_sources` | `route_schema` 主轴 |

核心规则是：

```text
场景复杂度 -> scenario
横向约束复杂度 -> facet
产品变化复杂度 -> SKU 实体属性
账号矩阵复杂度 -> account / persona
内容表达复杂度 -> production_specs / visual_style
治理复杂度 -> governance
```

## 六、目录治理的演进顺序

既然当前模型足够支撑近期业务，就不需要一次性引入完整未来系统

目录治理的目标不是一次性迁移所有真值，而是让当前模型先可读、可解释、可继续演进：

- 让 `route_schema` 成为分面单轴漏斗路由的阅读入口
- 让 `scenario` 主轴、`facet` 横轴、`SKU` 裁决和反向覆盖盘点清晰可见
- 保留 `entities`、`content_runtime`、`governance` 等未来扩展层，但不提前强行迁移所有内容
- 先建立导览层和读法，再按风险顺序渐进迁移真值文件

蓝图级演进顺序：

| 阶段 | 目标 | 迁移原则 |
| --- | --- | --- |
| 阶段 1 | 建立 `route_schema` 导览层 | 只统一阅读入口，不移动真值 |
| 阶段 2 | 拆清场景、分面、关键词的职责 | 先迁移低风险结构，再迁移高频真值 |
| 阶段 3 | 补齐 SKU 实体属性和资格字段 | 只扩展实体层，不改 `scenario` 主轴 |
| 阶段 4 | 引入账号和内容运行时结构 | 作为下游消费层，不反写路由主轴 |

## 七、架构健壮性判断

当前模型的健壮性来自四个设计点：

- 单一 `scenario` 主轴避免多轴嵌套树爆炸
- 平铺 `facet` 支持横向条件增长
- SKU 属性和硬闸支持产品承接变化
- 下游消费层保留账号、风格、合规和内容结构的扩展空间

它的鲁棒性来自三类门禁，而不是某几个具体脚本：

- 词表一致性门禁：保证人读结构和机器消费结构一致
- 路由漂移门禁：保证场景、关键词、实体裁决关系不分裂
- 下游消费门禁：保证 profile、内容生产和合规链路能稳定消费路由结果

因此，当前模型足以支撑近期业务演进；未来复杂度上升时，应沿扩展口演进，而不是提前推翻路由模型

## 八、总结

当前阶段最稳妥的策略不是过度设计，也不是停留在旧目录

更合理的做法是：

```text
保留当前分面单轴漏斗路由
-> 把目录治理到能清晰表达当前模型
-> 为 SKU 生命周期和账号矩阵保留扩展口
-> 等业务复杂度真正出现后再扩展对应层
```

一句话总结：

**当前路由模型足以支撑业务演进，目录治理要做的是让这个模型清晰、可读、可迁移，并为未来复杂度保留自然生长的位置**
