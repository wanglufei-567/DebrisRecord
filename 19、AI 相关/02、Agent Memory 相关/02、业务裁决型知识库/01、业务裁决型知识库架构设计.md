## 业务裁决型知识库架构设计

> 架构命名为**“分面单轴漏斗路由”**（Faceted Single-Axis Funnel Routing）
>
> 这个名字本身就是架构的记忆锚点：
>
> - **分面**：指人群、部位、分型、阶段、症状等维度平铺打标、相交收敛
> - **单轴**：指只有 `scenario` （场景）一根层级轴进入漏斗
> - **漏斗**：指场景下钻、`parent` （父场景）回退和人群硬闸收口
> - **路由**：指整条链路的目标是把自然语言输入稳定路由到正确的 **SKU**

### 一、旧架构的问题

当前项目要解决的核心问题，不是“再多补几个关键词”，而是**「关键词」**进入知识库后，如何稳定收敛到正确的**业务场景**、**约束条件**和 **SKU**

旧路由更接近“扁平两级桶”：

```text
用户输入
-> 关键词 / 触发词桶
-> 场景平桶
-> SKU 承接
```

这个架构在早期可以快速跑通，但随着业务方开始补充更细的场景、症状、人群和产品差异，问题会集中暴露

最直观的问题是：**输入看起来被系统接住了，但没有落到足够精准的子场景，最终 SKU 裁决也会跟着变粗**

例如：

- “甲状腺术后疤痕，脖子低头会拉扯”，如果只命中“术后”或“疤痕”，就会停在通用外科术后护理，而颈部刀口显眼、低头牵拉、衣领摩擦这些细场景痛点不会参与裁决
- “孩子摔伤后留疤，能不能用疤痕贴”，如果只命中“疤痕贴”或“外伤疤痕”，就可能沿用成人常规产品，而不是先识别儿童人群和儿童适用 **SKU**
- “剖腹产刀口疤怎么护理”，如果只命中“术后疤痕”，就会丢掉孕产 / 哺乳期约束，后续话术、禁忌和 **SKU** 候选都会变得过于通用

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-01-flat-vs-funnel.png" alt="diagram-01-flat-vs-funnel" style="zoom: 25%;" />

**旧架构**最关键的不是“节点数量少”而是太扁平，只有“关键词 -> 场景桶 -> **SKU**”这类**粗粒度路径**，导致**细粒度业务信息**无稳定位置可以沉淀

换句话说，旧架构不是分类不够多，而是**分类结构不够稳定**

**细粒度业务信息**只能临时塞进关键词、文案或代码分支里，无法成为可判断、可继承、可路由的知识库真值

这会带来四类问题：

1. **匹配机制失控：谁先匹配到，谁就拿走路由权**
   - 子串匹配只看字面重叠，不理解“甲状腺术后疤痕”到底是在讲部位、阶段还是疤痕问题
   - 最终落进哪个桶取决于触发词的匹配顺序，而不是业务语义
   - 表达越具体的长尾搜索词，反而越容易被更短的通用触发词截胡

2. **结构落点缺失：具体业务信息只能塞进触发词或文案**
   - “甲状腺术后”如果只作为 `surgery_postop` 平桶里的一个触发词，就不能沉淀自己的痛点、禁忌、话术和 **SKU** 候选
   - 颈部刀口显眼、低头牵拉、衣领摩擦这类细场景信息只能散落在文案或人工经验里，后续无法稳定复用

3. **约束优先级不足：特殊条件容易被普通规则覆盖**
   - 儿童、孕产、术后、敏感部位这类条件本来会直接影响 **SKU** 和话术边界，但旧架构里只是附着在某个场景桶里的弱提示
   - 一旦先命中通用规则，特殊条件就只能被动补充，无法稳定影响最终 **SKU** 和话术选择
   - 这类错误不是文案问题，而是旧结构没有把高优先级约束建模成稳定规则

4. **规则真值分裂：知识库写了，不等于运行时执行**
   - 如果 `taxonomies.json` 里维护一套 `sku_map`，代码里的 `choose_recipe` 又维护另一套路由逻辑，那么同一个场景可能在知识库里指向 A **SKU**，运行时却被代码判断成 B **SKU**
   - 这类问题的本质不是文档写错，而是业务规则没有收敛到唯一来源；后续补场景、改 **SKU**、加限制条件时，知识库和代码很容易不同步

所以目标架构要解决的问题可以压缩成一句话：==**把自然语言输入拆成“可判断的结构化条件”，再用“场景下钻 + facet 打标 / 横向收敛 + SKU 裁决”完成稳定路由**==

### 二、目标架构总览

**分面单轴漏斗路由** 不是把搜索词塞进更多分类桶，而是把**「关键词」**转成**可判断**、**可过滤**、**可继承**、**可裁决**的结构

整条链路可以先记成：

```text
人话输入
-> 模糊归一
-> 场景下钻
-> facet 打标 / 横向收敛
-> 字段回退
-> 硬闸裁决
-> SKU 收口
-> 下游消费
```

**LLM 负责听懂用户，场景漏斗负责定位问题，facet 负责叠加条件，SKU 规则负责做对决策，下游消费负责表达结果**

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-03-bidirectional-flow.png" alt="diagram-03-bidirectional-flow" style="zoom: 25%;" />

这张图是整篇文章的架构入口

它把当前知识库路由拆成八个步骤：

| 步骤 | 环节 | 解决的问题 | 产物 |
| --- | --- | --- | --- |
| 0 | 搜索词 / 关键词 | 用户真实表达是什么 | 原始输入 |
| 1 | 规范化 / 别名归一 | 用户表达对应哪些标准标签 | `scenario` / `facet` 候选 |
| 2 | 并行打标 / `facet` 识别 | 还有哪些横向约束 | 人群、部位、分型、阶段、症状 |
| 3 | 场景命中 | 属于哪个业务场景 | 最深子场景 |
| 4 | `parent` 回退 | 子场景缺什么默认信息 | 父节点继承字段 |
| 5 | 人群硬闸 | 哪些产品绝不能进入候选 | 过滤后的候选集 |
| 6 | **SKU** 裁决 | 最终选哪个产品承接 | 目标 **SKU** |
| 7 | 下游消费 | 内容怎么表达和交付 | 文案、风格、标签、合规 |

表格顺序表达的是逻辑依赖，不是执行时序：第 2 步 **facet 打标**和第 3 步**场景命中**可以并行执行，前文链路里“**场景下钻** -> **facet 打标 / 横向收敛**”的线性写法同理

这个总览有三个重要边界：

1. 第 0 到第 1 步：解决“听懂用户”
   - 这里可以使用向量、语义匹配或 **LLM**，因为用户不会严格按知识库标准词输入
2. 第 2 到第 6 步：解决“做对决策”
   - 这里要靠**显式结构和规则**，因为人群、禁忌、合规和 **SKU** 适配不能交给相似度猜测
3. 第 7 步之后已经进入内容生产，不再属于路由主轴
   - 内容类型、风格、标签、合规可以消费路由结果，但不能反过来定义 **scenario** 主轴、`facet` 轴或 **SKU** 裁决

### 三、原则一：单轴漏斗

**单轴漏斗** 的核心是：**漏斗深度只给一根真正有父子包含关系、并且需要字段继承的轴**

在当前项目里，这根轴是 `scenario`

原因不是为了方便人类理解，也不是因为其他轴不重要，而是因为场景最符合层级漏斗的两个条件：

- 真有 `is-a` 嵌套，例如术后场景 -> 外科术后 -> 甲状腺术后
- 确实需要 `parent` 回退，例如子场景缺少通用护理原则时，可以向父场景继承

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-05-relationship-types.png" alt="diagram-05-relationship-types" style="zoom:25%;" />

设计任何路由轴之前，先判断关系

| 关系 | 判断方式 | 当前项目处理 |
| --- | --- | --- |
| 包含关系 | A 是 B 的一种 | 可以进入层级树，例如外科术后 -> 甲状腺术后 |
| 并列关系 | 两者同属一轴，通常二选一 | 保持同轴兄弟，不跨轴混用 |
| 正交关系 | 两者可以同时成立 | 做平铺 `facet`，运行时相交过滤 |

如果把多个正交轴强行套进一棵树，就会得到组合爆炸

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-04-tree-explosion-vs-facet.png" alt="diagram-04-tree-explosion-vs-facet" style="zoom:25%;" />

多轴嵌套的问题在于：

- 叶子数等于场景 × 人群 × 分型 × 阶段 × 部位
- 任一轴新增一个值，整棵树都要扩张
- 同一个约束会在不同分支下重复维护
- 业务补一条信息，可能变成一轮架构调整

所以当前项目把 **scenario** 留在纵向漏斗里，把人群、部位、分型、阶段、症状等保持为平铺 `facet`

这不是降低精度，而是把精度从“**穷举叶子节点**”转移到“**运行时条件组合**”

参考 **OLAP** 的说法，`scenario` 下钻类似 `drill-down`，`parent` 回退类似 `roll-up`，平铺 `facet` 更像查询条件组合，不是新的层级轴

### 四、原则二：四类元素分离

知识库路由里不是所有东西都应该进入同一棵树

当前项目需要把元素分成四类：路由主轴、正交 `facet`、实体属性、下游消费

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-02-four-elements.png" alt="diagram-02-four-elements" style="zoom:25%;" />

| 类别 | 回答的问题 | 组织方式 |
| --- | --- | --- |
| `scenario` 场景主轴 | 用户处在什么业务场景 | 唯一层级漏斗 |
| 平铺 `facet` | 用户还有哪些横向约束 | 平铺字段，相交过滤 |
| **SKU** / **SKU** 属性 | 哪个产品能承接 | 产品实体和属性卡 |
| 下游消费 | 选定后怎么表达、怎么交付 | 各自成体系，不回写主轴 |

这里的边界可以压缩成一句话：**scenario 管定位场景，facet 管叠加条件，SKU 管产品裁决，下游消费管表达与交付**

这个边界之所以重要，是因为==**自然语言**经常把多个维度的信息揉在一个词里==

- 例如，“剖腹产疤痕”一个词同时暗示场景（产后）、部位（腹部）和成因（手术创伤），塞进任何单一分类桶都会丢掉另外两个维度


所以，==好的**知识库路由**不是把混合词硬塞进某个桶，而是先按**维度**拆成**职责单一的原子标签**，再靠**正交组合**还原原意==

记忆版：**混合词要拆轴，单一轴才可组合**

### 五、原则三：一图双向

**一图双向** 解决的是“知识库不要维护两套真值”

同一套 **KB Schema**，正向可以做**内容生成路由**，反向可以做**选题覆盖盘点**

- 正向：用户搜什么 -> 命中什么场景 -> 过滤什么条件 -> 选择什么 **SKU**
- 反向：一个 **SKU** -> 适合哪些人群 / 场景 / 症状 -> 应该覆盖哪些关键词

回看目标架构总览图：

<img src="https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/diagram-03-bidirectional-flow.png" alt="diagram-03-bidirectional-flow" style="zoom:25%;" />

如果生成侧、运营侧、文案侧和代码侧各自维护一套表，短期看只是重复，长期会变成真值漂移

“漂移”不是抽象的工程洁癖，而是同一个业务事实在不同地方变成了不同版本

| 方向 | 常见形态 | 漂移后会发生什么 |
| --- | --- | --- |
| 生成侧 | `keyword -> scenario -> SKU` | 运营新增关键词后，生成侧不识别，用户搜得到但系统路由不到 |
| 运营侧 | `SKU -> 人群 -> 场景 -> 关键词` | 生成规则更新后，运营覆盖表没有同步，盘点出来的机会和真实生成能力不一致 |
| 文案侧 | 选题模板 / 标签规则 | 内容能写出来，但不一定对应正确 **SKU** |
| 代码侧 | `choose_recipe` 硬编码 | 代码实际选择结果和知识库 `sku_map` 不一致 |

漂移会导致三个具体问题：

- **决策错误**：该给儿童 **SKU** 时给了成人产品
- **覆盖误判**：以为某个场景已覆盖，实际只是运营表里有，生成侧没有
- **维护失控**：每次补业务信息，都要追着多张表、多段代码同步，漏一处就产生新冲突

一图双向的目标不是让结构看起来更优雅，而是避免一套业务事实在多个地方变成多个半真值

**同一张结构正向用于决策，反向用于盘点；生成和运营不再各维护一套真值**

### 六、关键机制

#### 6.1、模糊归一

**「模糊归一」**解决的问题是：**==用户不会按知识库标准词说话，所以系统要先把自然语言翻译成标准标签==**

例如，用户可能会说：

```text
脖子开刀留下的印子
甲状腺刀口疤
喉咙下面手术疤
脖子术后疤
```

这些表达表面不同，但可能都要归一到：

```text
scenario = 甲状腺术后 / 外科术后
body_part = 颈部
cause = 手术创伤
```

- 为什么叫**“模糊”**：因为用户表达可能包含别名、口语、错别字、省略词，也可能一个词同时暗示多个维度


- 为什么叫**“归一”**：因为最终必须落到**受控词表**，不能让“脖子”“颈部”“喉咙下面”在系统里各自乱飞


这里的“打标”不是 **LLM** 自由生成一组标签，也不是代码里写死“甲状腺术后应该走哪个 **SKU**”

更准确的理解是：==**知识库维护语义映射，编译器把映射变成运行时词表，代码用确定性算法消费这份词表，把人话归一成系统受控值**==

这条链路分成四步：

1. **源文件维护语义映射**

   场景相关的语义映射维护在每个 `scenario` 节点里

   例如，甲状腺术后场景节点文件中的 **schema** 部分会声明：

   ```yaml
   scenario_key: thyroid_postop
   parent: surgery_postop
   aliases: [甲状腺, 甲状腺术后, 脖子开刀, 颈部手术疤]
   facet_defaults:
     body_part: neck
   ```

   这段信息表达三件事：

   - 用户说“甲状腺”“甲状腺术后”“脖子开刀”，都可以归一到 `scenario = thyroid_postop`
   - `thyroid_postop` 是 `surgery_postop` 的子场景，命中后仍然可以向父场景继承通用信息
   - 这个子场景默认暗示 `body_part = neck`

   横向条件的语义映射维护在独立 `facet` 词表里，例如，部位词表会声明：

   ```yaml
   entries:
     - key: neck
       match: [颈部, 脖子, 喉咙下面]
     - key: face
       match: [脸, 面部, 额头, 下巴]
   ```

   这段信息表达的是：

   - 用户说“脖子” “颈部” “喉咙下面”，都可以归一到 `body_part = neck`
   - `body_part` 只是横向 `facet`，不会进入 `scenario` 场景树
   - 它可以和任何场景相交，例如 `thyroid_postop + neck`，也可以是 `burn_trauma + neck`

2. **编译器生成运行时词表**

   运行时代码不适合每次逐个读取 **Markdown** 文件，所以会把场景节点和 `facet` 词表编译成机器可消费的词表 `taxonomies.json`

   简化后可以理解成：

   ```json
   {
     "scenarios": {
       "surgery_postop": ["术后", "手术后", "外科术后"],
       "thyroid_postop": ["甲状腺", "甲状腺术后", "脖子开刀", "颈部手术疤"]
     },
     "scenario_parents": {
       "thyroid_postop": "surgery_postop"
     },
     "facets": {
       "body_part": {
         "neck": ["颈部", "脖子", "喉咙下面"]
       }
     },
     "sku_map": {
       "surgery_postop": ["scar_patch", "self_drying_silicone_gel"]
     }
   }
   ```

   所以 **taxonomies.json** 不是另一份人工真值，而是“**知识库源文件编译后的运行时索引”**

3. **代码消费词表并执行确定性命中**

   运行时代码消费 `taxonomies.json` 时，做的是传统程序逻辑：

   ```text
   读取 taxonomies.json
   -> 遍历 scenarios 和 facets
   -> 判断用户输入是否包含某个 alias
   -> 命中后归一成对应 key
   -> 同一个 facet 轴内取最长命中
   -> scenario 命中时优先选择更深子场景
   -> 同深度场景再选择更长别名
   -> 输出确定的 scenario / facet
   ```

   这里的“子串命中”可以理解成：

   ```text
   alias in 用户输入
   ```

   当前实现不是靠正则解析，也不是靠 **LLM** 实时自由判断，而是读取知识库编译出的别名词表，然后做确定性匹配

4. **一次用户输入被归一成稳定结构**

   例如用户输入：

   ```text
   甲状腺术后疤痕，脖子低头会拉扯
   ```

   运行时代码会在 `scenarios` 中看到多个候选：

   ```text
   术后 -> surgery_postop
   甲状腺术后 -> thyroid_postop
   ```

   如果只按旧架构的子串顺序，可能先命中“术后”，然后停在通用 `surgery_postop`

   目标实现不会停在这里，而是继续比较场景深度：

   ```text
   surgery_postop 深度更浅
   thyroid_postop 是 surgery_postop 的子场景，深度更深
   ```

   所以最终场景命中是：

   ```text
   scenario = thyroid_postop
   ```

   同时，代码会在 `facets.body_part` 中命中：

   ```text
   脖子 -> body_part = neck
   ```

   如果后续代码读取场景节点的 `facet_defaults`，还可以从 `thyroid_postop` 补出：

   ```text
   body_part = neck
   ```

   最终这句话会被归一成更稳定的结构：

   ```text
   scenario = thyroid_postop
   parent = surgery_postop
   body_part = neck
   stage = postop
   symptom = 牵拉
   ```

   后面的 `parent` 回退、相交过滤和 **SKU** 裁决，都是基于这些受控值继续执行

这里最关键的认知是：**业务含义不写死在代码里，但命中、优先级、回退、过滤、裁决这些执行规则写在代码里**

这样既保留知识库可维护性，也保留程序可控性

==**模糊归一负责听懂用户，后面的规则负责做对决策**==

#### 6.2、parent 字段级回退

**「parent 字段级回退」**解决的问题是：**==子场景要足够细，但不能为了变细就把父场景里的通用知识全部复制一遍==**

它最容易被误解成“命中子场景失败后，退回父场景”

但真实含义不是这样

**命中甲状腺术后时，最终场景仍然是 `thyroid_postop`，不会被替换成 `surgery_postop`；只是当某个字段在子场景里缺失时，才沿 `parent` 向父场景取默认值**

这条机制可以分成四步理解：

1. **源文件先声明父子关系**

   甲状腺术后节点会声明自己是外科术后的子场景：

   ```yaml
   scenario_key: thyroid_postop
   parent: surgery_postop
   aliases: [甲状腺, 甲状腺术后, 脖子开刀, 颈部手术疤]
   facet_defaults:
     body_part: neck
   related_products: []   # 缺省继承父场景候选池
   ```

   外科术后节点则维护通用候选池和通用注意事项：

   ```yaml
   scenario_key: surgery_postop
   parent: null
   aliases: [术后, 手术, 缝针]
   related_products:
     - /entities/skus/scar_patch
     - /entities/skus/jiuyuan_silicone_gel
     - /entities/skus/self_drying_silicone_gel
   ```

   这表达的是：`thyroid_postop` 有自己的专属痛点和别名，但它仍然属于 `surgery_postop`，可以复用父场景里的通用候选 **SKU** 和通用护理边界

2. **编译产物保留父子索引**

   编译到 `taxonomies.json` 后，父子关系会变成机器可读结构：

   ```json
   {
     "scenario_parents": {
       "thyroid_postop": "surgery_postop"
     },
     "sku_map": {
       "surgery_postop": [
         "self_drying_silicone_gel",
         "jiuyuan_silicone_gel",
         "scar_patch"
       ]
     }
   }
   ```

   注意这里有一个关键现象：`thyroid_postop` 可以没有自己的 `sku_map`，这不是信息缺失，而是设计选择

   - 因为甲状腺术后当前没有专属产品池时，可以先继承外科术后的通用产品池
   - 以后如果业务确认它有专属优先级，再给 `thyroid_postop` 单独补字段

3. **运行时代码沿 `parent` 链找字段**

   当前运行时最明确落地的是候选 **SKU** 池回退

   代码逻辑可以简化理解成：

   ```text
   resolve_pool(thyroid_postop)
   -> 查 sku_map.thyroid_postop
   -> 没有
   -> 查 scenario_parents.thyroid_postop = surgery_postop
   -> 查 sku_map.surgery_postop
   -> 返回父场景候选池
   ```

   这不是把 `scenario` 改成父场景，而是只把“候选 **SKU** 池”这个字段从父场景拿过来

   所以最终结构更接近：

   ```text
   scenario = thyroid_postop
   parent = surgery_postop
   sku_pool = surgery_postop.sku_map
   ```

4. **字段级回退保留子场景特殊性**

   `parent` 回退的关键不是“能不能复用父节点”，而是“复用父节点时不能抹掉子节点”

   | 信息字段 | 子场景有值 | 父场景有值 | 最终使用 |
   | --- | --- | --- | --- |
   | 专属痛点 | 有 | 有通用痛点 | 用子场景 |
   | 部位默认值 | 有 `body_part = neck` | 无或更泛 | 用子场景 |
   | 通用护理原则 | 缺失 | 有 | 从父场景继承 |
   | 候选 **SKU** | 缺失 | 有通用候选池 | 从父场景继承 |
   | 禁忌边界 | 子场景有明确排除 | 父场景有通用规则 | 子场景排除优先 |

   规则可以记成：

   - 子节点有值，用子节点
   - 子节点缺值，向父节点补
   - 子节点明确覆盖，以子节点为准
   - 子节点明确排除，不能被父节点重新加回来

一次完整命中可以这样看：

```text
用户输入：甲状腺术后疤痕怎么护理

模糊归一：
scenario = thyroid_postop
body_part = neck

字段级回退：
thyroid_postop 没有独立 sku_map
-> 沿 parent 找到 surgery_postop
-> 继承 surgery_postop 的候选 SKU 池

最终结果：
scenario 仍然是 thyroid_postop
专属痛点用 thyroid_postop
候选 SKU 池暂用 surgery_postop
后续再做人群硬闸和 SKU 裁决
```

这就是场景树有意义的原因：它不是为了分类好看，而是为了让更细场景继承通用知识，同时保留自己的特殊性

#### 6.3、平铺打标与相交收敛

**「平铺打标与相交收敛」**解决的问题是：**==用户输入里经常同时包含场景、人群、部位、阶段、症状和分型，但这些维度不是同一棵树上的父子关系==**

如果把它们全部做成层级树，就会变成：

```text
术后
-> 儿童术后
-> 儿童颈部术后
-> 儿童颈部术后增生
-> 儿童颈部术后增生发痒
```

这会迅速产生组合爆炸，也会让同一个约束在多个分支里重复维护

正确做法是：**只有 `scenario` 进入纵向漏斗，其他横向约束保持为平铺 `facet`，运行时再相交收敛**

这条机制可以分成四步理解：

1. **先判断一个概念是不是 `facet`**

   一个概念如果能和多个场景同时成立，就优先考虑作为 `facet`

   例如：

   - `children` 可以和儿童磕碰、烫伤外伤、术后护理同时成立
   - `neck` 可以和甲状腺术后、外伤、摩擦部位同时成立
   - `proliferative` 可以和剖腹产、外科术后、儿童磕碰同时成立
   - `itch` 可以出现在术后疤痕、烫伤疤痕、增生疤痕等多个场景里

   所以这些概念不应该进入 `scenario` 场景树，否则场景树会从“业务场景轴”膨胀成“所有条件组合轴”

2. **源文件用独立词表维护每个横向轴**

   人群、部位、阶段、症状、疤痕分型各自维护自己的 `facet` 词表

   例如，人群词表：

   ```yaml
   entries:
     - key: children
       match: [儿童, 孩子, 宝宝, 娃, 小朋友, 学生]
     - key: pregnant_lactating
       match: [孕妇, 孕期, 哺乳期, 产后, 宝妈, 备孕]
     - key: adult
       match: []
   ```

   部位词表：

   ```yaml
   entries:
     - key: neck
       match: [颈部, 脖子, 喉咙下面]
     - key: face
       match: [脸, 面部, 额头, 下巴]
   ```

   症状词表：

   ```yaml
   entries:
     - key: itch
       match: [痒, 发痒, 越挠越痒]
     - key: raised
       match: [凸起, 鼓起, 凸出来]
   ```

   这些词表表达的是同一个原则：**每个轴只回答自己负责的问题，不把别的轴混进来**

3. **运行时按轴打标，而不是生成新场景**

   运行时代码读取 `taxonomies.json` 里的 `facets`，逐轴扫描用户输入

   逻辑可以简化理解成：

   ```text
   detect_facets(text)
   -> 遍历 population / body_part / stage / symptom / scar_type
   -> 每个轴内部做 alias 子串命中
   -> 同一轴命中多个别名时取最长命中
   -> 输出一组平铺 facet
   ```

   例如用户输入：

   ```text
   孩子甲状腺术后疤痕，脖子这里有点凸起发痒
   ```

   可能得到：

   ```text
   scenario = thyroid_postop
   population = children
   body_part = neck
   symptom = itch / raised
   ```

   这里不会生成一个新场景 `children_thyroid_postop_neck_itch`

   因为“儿童”“脖子”“发痒”“凸起”都是横向条件，不是新的场景主轴

4. **相交收敛把多个条件合在一起做决策**

   平铺打标只是把输入拆成多个稳定字段，相交收敛才是这些字段发挥作用的地方

   用关系数据库类比，平铺打标相当于给对象填字段，相交收敛相当于用 **WHERE** 条件做过滤：

   ```sql
   WHERE scenario = 'thyroid_postop'
     AND population = 'children'
     AND body_part = 'neck'
     AND symptom IN ('itch', 'raised')
   ```

   这里的关键不是要把项目改成数据库，而是借用数据库已经成熟的认知：==**用独立的轴描述对象，再用谓词筛选对象**==

   在当前路由里，`facet` 对后续链路的影响分层发生：

   - `population = children` 会进入人群硬闸，影响哪些 **SKU** 有资格进入候选
   - `body_part = neck` 会影响场景解释、内容表达和视觉边界
   - `stage = unhealed / scabbing` 会影响是否能谈祛疤产品，还是必须先提示创面护理
   - `symptom = itch / raised` 更偏向痛点表达和内容结构，不直接决定 **SKU**

所以 `facet` 不是“弱化版场景”，也不是“补充描述词”

它是和 `scenario` 正交的条件层：==**scenario 负责定位问题，facet 负责叠加约束，后续规则再决定这些约束如何影响 SKU、话术和下游表达**==

#### 6.4、人群硬闸与 SKU 裁决

**「人群硬闸与 SKU 裁决」**解决的问题是：**==路由已经知道用户在哪个场景、有哪些约束之后，最终哪些产品有资格承接，以及在有资格的产品里选谁==**

它是漏斗的收口，也是第一节里“儿童 **SKU** 被成人常规产品兜底覆盖”问题的直接解法

这里要先区分两个概念：

- `facet` 条件收敛回答“候选有多匹配”
- 硬闸回答“候选有没有资格”

所以硬闸不是排序权重，而是一票否决

一个 **SKU** 只要命中禁忌人群，即使它和场景、症状、模板都很匹配，也必须出局

这条机制可以分成四步理解：

1. **SKU 实体维护承接资格**

   产品能不能承接，不应该写进 `scenario` 场景树，而应该挂在 **SKU** 实体上

   例如成人常规疤痕贴可能声明：

   ```yaml
   sku_id: scar_patch
   population_gate:
     suitable: [adult, pregnant_lactating]
     forbidden: [children]
   stage_gate: healed_only
   routable: true
   ```

   儿童疤痕护理产品可能声明：

   ```yaml
   sku_id: children_scar_gel
   population_gate:
     suitable: [children]
     forbidden: []
   stage_gate: healed_only
   routable: true
   ```

   这些字段表达的是产品自己的承接资格，而不是某个场景的分类属性

   这样设计有两个原因：

   - 同一个 **SKU** 会被多个场景引用，属性挂在实体上只需维护一份
   - 场景树负责回答**“用户在哪里**”，产品实体负责回答“**我能不能承接**”

2. **运行时代码先拿到候选池**

   候选池来自 `scenario` 命中和 `parent` 回退

   例如：

   ```text
   scenario = thyroid_postop
   -> thyroid_postop 没有独立 sku_map
   -> 沿 parent 回退到 surgery_postop
   -> 得到父场景候选池：
      self_drying_silicone_gel
      jiuyuan_silicone_gel
      scar_patch
   ```

   到这里为止，系统只是知道“这些产品和外科术后场景相关”

   它还没有判断这些产品对当前人群是否有资格

3. **硬闸先于任何排序和模板兜底**

   如果前面 `facet` 打标得到：

   ```text
   population = children
   ```

   那么运行时代码会检查候选池里每个 **SKU** 的 `population_gate.forbidden`

   简化逻辑是：

   ```text
   hard_gate(pool, population)
   -> 遍历候选 SKU
   -> 如果 routable = false，出局
   -> 如果 population 在 forbidden 里，出局
   -> 剩下的 SKU 才能进入裁决
   ```

   如果候选池里某个成人产品写了：

   ```yaml
   forbidden: [children]
   ```

   那么它无论场景多匹配、模板多需要、排序多靠前，都不能进入最终结果

   这就是“一票否决”

4. **SKU 裁决只在过闸候选中发生**

   硬闸之后才轮到 **SKU** 裁决

   裁决顺序可以理解成：

   ```text
   场景命中
   -> parent 回退得到候选池
   -> 人群 / 阶段 / routable 硬闸过滤
   -> 在剩余候选中按场景优先级和模板需求选择 SKU
   -> 如果模板需要补位，补位 SKU 也必须再次过硬闸
   -> 过闸后仍不足，就降级模板，而不是加回被否决 SKU
   ```

   例如，“儿童疤痕贴和凝胶哪个好”是对比模板，模板天然希望有两个产品做比较

   但如果儿童人群硬闸后只剩一个儿童适用产品，系统应该降级成单品页或保守建议，而不是为了凑对比，把成人疤痕贴重新加回来

   这就是“资格永远先于表达形式”

一次完整裁决可以这样看：

```text
用户输入：孩子术后疤痕贴和凝胶哪个好

模糊归一：
population = children
scenario = surgery_postop / children_bump 候选
template = comparison

候选池：
children_bump -> children_scar_gel
或 surgery_postop -> adult 常规候选池

硬闸：
children 命中成人 SKU forbidden
-> 成人常规产品出局
-> children_scar_gel 保留

SKU 裁决：
过闸候选不足两个
-> 不强行补成人 SKU
-> 降级为儿童单品承接或保守建议
```

这里的核心不是“儿童产品排序更高”，而是“成人禁用产品没有资格参与排序”

记忆版：==**facet 收窄是排序问题，硬闸出局是资格问题，资格永远先于排序，资格也先于模板兜底**==

#### 6.5、`taxonomies.json` 的运行时消费链路

前面四个机制分别解释了“怎么归一”“怎么回退”“怎么打标”“怎么裁决”

但运行时不是把这些机制分开执行给人看，而是在一次用户输入里连续发生

这一节不引入新原则，只用一个最小例子把消费词表的链路串起来

假设用户输入是：

```text
孩子甲状腺术后疤痕，脖子低头会拉扯，疤痕贴和凝胶哪个好
```

简化后的 `taxonomies.json` 可以理解成：

```json
{
  "scenarios": {
    "surgery_postop": ["术后", "手术后", "外科术后"],
    "thyroid_postop": ["甲状腺", "甲状腺术后", "脖子开刀", "颈部手术疤"]
  },
  "scenario_parents": {
    "thyroid_postop": "surgery_postop"
  },
  "facets": {
    "population": {
      "children": ["儿童", "孩子", "宝宝", "娃"]
    },
    "body_part": {
      "neck": ["颈部", "脖子", "喉咙下面"]
    },
    "symptom": {
      "raised": ["凸起", "鼓起", "凸出来"],
      "itch": ["痒", "发痒", "越挠越痒"]
    }
  },
  "sku_map": {
    "surgery_postop": ["self_drying_silicone_gel", "jiuyuan_silicone_gel", "scar_patch"]
  }
}
```

同时，**SKU** 实体上会有资格字段：

```yaml
scar_patch:
  population_gate:
    forbidden: [children]
  routable: true

children_scar_gel:
  population_gate:
    forbidden: []
  routable: true
```

这次输入的运行时链路可以拆成八步：

1. **读取消费词表**

   运行时代码先读取 `taxonomies.json`，拿到 `scenarios`、`scenario_parents`、`facets` 和 `sku_map`

   代码不需要知道“甲状腺术后为什么属于外科术后”，它只消费编译后的索引结构

2. **遍历 `scenarios` 做场景候选命中**

   代码逐个检查：

   ```text
   "术后" in 用户输入 -> 命中 surgery_postop
   "甲状腺" in 用户输入 -> 命中 thyroid_postop
   "甲状腺术后" in 用户输入 -> 命中 thyroid_postop
   ```

   到这一步只是得到候选，还没有最终裁决场景

3. **按“更深场景优先，同深更长别名优先”确定 `scenario`**

   候选可以理解成：

   ```text
   术后:
     scenario = surgery_postop
     depth = 0
     alias_len = 2

   甲状腺:
     scenario = thyroid_postop
     depth = 1
     alias_len = 3

   甲状腺术后:
     scenario = thyroid_postop
     depth = 1
     alias_len = 5
   ```

   因为 `thyroid_postop` 是 `surgery_postop` 的子场景，所以深度更深

   同属 `thyroid_postop` 时，“甲状腺术后”比“甲状腺”更长，携带的信息更具体

   最终得到：

   ```text
   scenario = thyroid_postop
   parent = surgery_postop
   ```

   这里的“更长别名优先”不是 **LLM** 式语义评分，而是用“命中片段越具体，越可能代表真实意图”这个规则近似表达匹配精度

4. **遍历 `facets` 做平铺打标**

   代码再逐轴扫描横向条件：

   ```text
   population.children:
     "孩子" in 用户输入 -> population = children

   body_part.neck:
     "脖子" in 用户输入 -> body_part = neck

   symptom.raised / symptom.itch:
     本句没有直接命中“凸起”“痒”，所以不强行补 symptom
   ```

   到这里，系统不会生成新场景 `children_thyroid_postop_neck`

   它会保留平铺结构：

   ```text
   scenario = thyroid_postop
   population = children
   body_part = neck
   ```

5. **根据 `scenario` 查 SKU 候选池**

   代码先查：

   ```text
   sku_map.thyroid_postop
   ```

   如果子场景没有独立候选池，就沿 `parent` 回退：

   ```text
   thyroid_postop
   -> parent = surgery_postop
   -> sku_map.surgery_postop
   ```

   得到候选池：

   ```text
   self_drying_silicone_gel
   jiuyuan_silicone_gel
   scar_patch
   ```

   注意，回退的是“候选 **SKU** 池”这个字段，不是把 `scenario` 改成 `surgery_postop`

6. **读取 SKU gate 做资格过滤**

   前面已经打出：

   ```text
   population = children
   ```

   所以候选池里的每个 **SKU** 都要检查：

   ```text
   routable 是否为 false
   population 是否命中 forbidden
   ```

   如果成人产品写了：

   ```yaml
   forbidden: [children]
   ```

   它就直接出局

   这一步不是排序，而是资格判断

7. **模板需求只能在过闸候选里补位**

   用户问“疤痕贴和凝胶哪个好”，模板可能被识别成对比型

   对比型天然希望有两个产品

   但如果儿童人群硬闸后只剩一个儿童可用产品，系统不能为了凑对比，把成人 **SKU** 加回来

   正确处理是：

   ```text
   过闸候选不足两个
   -> 不加回 forbidden SKU
   -> 降级为单品承接或保守建议
   ```

8. **输出稳定的路由中间态**

   这一轮运行的结果不是一段文案，而是一组可继续消费的结构化结果：

   ```text
   scenario = thyroid_postop
   parent = surgery_postop
   facets:
     population = children
     body_part = neck
   sku_pool:
     从 surgery_postop 回退得到
   hard_gate:
     成人 children-forbidden SKU 出局
   template:
     comparison 不满足时降级
   ```

   后续下游消费层再根据这组结果决定文案、风格、合规和交付形式

这条链路最关键的认知是：**`taxonomies.json` 是运行时索引，代码是确定性解释器，业务含义来自知识库，最终结果由规则链路收敛**

### 七、下游消费层边界

下游消费层负责“选定后怎么表达”，不是负责“主路由怎么定义”

例如：

- 标签分层
- 爆文共性刻度
- 选题双高
- 内容类型
- 风格树
- 合规护栏

这些内容可以消费路由结果，用于决定标题、标签、风格、合规表达和内容结构

消费方式举例：

- **内容类型** 和 **风格树** 按命中的 `scenario` 选表达框架和基调

- **合规护栏 ** 按 **population** 和 **SKU** 属性收紧措辞边界

- **选题双高** 和 **爆文共性刻度** 按反向盘点结果决定优先覆盖哪些关键词

  > - **选题双高**：常指一个关键词 / 选题同时满足两类高价值条件，**高搜索价值** 和 **高承接价值**
  >   - 理解成：用户有人搜 + 品牌能承接
  > - **爆文共性刻度**：指从爆款内容里抽出来的一组可复用特征，用来判断一个选题或内容结构是否更像高表现笔记
  >   - 理解成：这个选题怎么写，更容易成为爆文
  > - **选题双高** 决定“值不值得优先写”，**爆文共性刻度** 决定“怎么写更像有效内容”
  >   - 路由结构已经知道：某个 **SKU** 适合哪些场景 / 人群 / 症状
  >   - 反向盘点发现：哪些场景或关键词还没覆盖
  >   - 然后运营侧再用：
  >     - 选题双高 = 哪些词又有搜索价值又能业务承接
  >     - 爆文共性刻度 = 哪些词更适合做爆款内容结构
  >   - 最终决定：先写哪些关键词、用什么内容结构写

但它们不能反过来定义 **scenario** 主轴，也不能把内容运营概念写回 **SKU** 裁决逻辑

正式架构的主线仍然是：

```text
模糊归一
-> scenario 下钻
-> facet 相交
-> parent 回退
-> 人群硬闸
-> SKU 裁决
```

### 八、横切治理材料

真值溯源、`exemplars` 示例库、竞品样本这类材料不属于漏斗的任何一层，它们横切喂养各层，但不构成新的主轴

| 材料 | 喂养对象 | 不允许做的事 |
| --- | --- | --- |
| 真值溯源 | 场景节点和 **SKU** 属性里的每条业务事实 | 不替代 schema 成为查询入口 |
| `exemplars` | 归一层的别名词表、下游的表达风格 | 不直接参与路由判断 |
| 竞品样本 | 场景痛点补全、关键词覆盖盘点 | 不把竞品的分类体系反向写入 **scenario** 主轴 |

判断一份材料是否属于横切治理很简单：把它删掉，路由结构仍然完整，只是内容质量和可信度下降

如果删掉它路由就断了，说明它其实是主轴或 `facet` 的一部分，应该正式建模

### 九、架构定位与边界

#### 9.1、定位与边界

**分面单轴漏斗路由** 的价值不在于概念新，而在于把几类**成熟工程思想**组合成一套**可维护**、**可解释**、**可测试**的**业务决策层**

- 如果从“学术新颖性”看，它不是最前沿概念
  - 受控词表、分面分类、规则引擎、字段继承、确定性路由都不是新东西

- 但如果从“业务工程成熟度”看，它的价值很高
  - 因为它解决的是普通 **LLM** 或普通 **RAG** 很难稳定承担的问题：==**把不稳定的人话输入，裁决成稳定、可复验、可审计的业务动作**==

**它真正厉害的地方**，是把 **LLM**、**知识库**、**规则**、**运行时代码**和**业务裁决**边界拆清楚了

它组合了四类能力：

1. **受控词表**
   - 用户表达可以是开放的，但==系统内部必须落到稳定标签==
   - 这解决“人话不稳定，系统要稳定”的问题
2. **分面分类**
   - 人群、部位、阶段、症状不强行塞进一棵树，而是作为横向 `facet` 组合
   - 这解决“多轴组合爆炸”的问题，和**经典分面分类思想**一致
3. **单轴漏斗**
   - 只有真正有父子继承关系的 `scenario` 进入层级
   - 这解决“细场景需要继承通用知识，同时保留自身特殊性”的问题，避免“场景 × 人群 × 部位 × 阶段”组合爆炸
4. **确定性运行时**
   - `taxonomies.json` 是机器消费索引，代码负责命中、回退、过滤和裁决
   - 这解决“**知识库可维护，运行结果可审计**”的问题，让系统结果可解释、可测试、可审计

这套组合的结果是：**业务含义可以持续维护在知识库里，但最终决策不会完全交给模型相似度或自由生成**

这对 **医药 sku** 这类业务非常关键

因为系统不是只要“回答得像”，而是要在儿童、孕产、术后、敏感部位、合规边界、**SKU** 适配这些场景里“做对决策”

因此，它更适合承担业务裁决任务，而不是承担所有知识问答任务

适合它的场景包括：

- 产品推荐
- 多 **SKU** 裁决
- 特殊人群规则
- 合规和禁忌边界
- 需要稳定复验的业务决策

不适合只靠它解决的场景包括：

- 开放问答
- 跨文档摘要
- 大规模资料检索
- 新资料证据引用
- 跨大量文本的关系发现
- 用户问题没有进入词表时的冷启动理解

**它不厉害的地方**，也要客观看到限制：

- 当前子串匹配本身不高级，召回能力有限
- 维护 `aliases` 和 `facet` 词表需要持续治理
- 新业务表达如果没有进入词表，系统可能识别不到
- 如果问题变成开放问答、跨文档推理、资料摘要，它不如 **RAG / GraphRAG** 自然
- 如果业务维度继续膨胀，`facet` 设计和 **SKU** gate 会变成长期治理负担

所以它不是“**AI** 时代的终极知识库架构”

它更准确的定位是：==**一个面向业务裁决的确定性知识路由层**==

#### 9.2、和 **RAG** 的关系

**分面单轴漏斗路由** 和 **RAG** 的边界：

- **RAG** 解决的是“从资料里找证据”，适合把外部文档、事实片段、案例和出处交给 **LLM** 生成答案

- **分面单轴漏斗路由** 解决的是“**把用户意图稳定裁决到业务动作**”，适合把自然语言输入归一成 **scenario**、**facet** 和 **SKU** 决策

两者不是替代关系，而是分层关系

- 普通 **RAG** 擅长回答：

  - 哪些资料和这个问题相关

  - 某个事实在哪里出现过

  - 多份材料可以怎样总结

  - 某个答案是否有可引用出处


- **分面单轴漏斗路由**擅长回答：

  - 这个用户输入属于哪个业务场景

  - 还有哪些横向约束必须同时考虑

  - 哪些 **SKU** 有资格进入候选

  - 特殊人群和禁忌边界能不能一票否决

  - 最终应该由哪个产品、话术和下游模板承接

#### 9.3、**和 GraphRAG 的关系**

**GraphRAG** 其实也说明了一个趋势：大家都发现“纯向量召回 + 文本片段”不够，需要**更结构化的知识组织**

微软 **GraphRAG** 文档明确说，它是比普通语义搜索更结构化、层级化的 **RAG** 方法，会抽取知识图谱、社区层级和摘要，用来处理普通 **RAG** 不擅长的复杂连接和全局理解问题 ，来源：[Microsoft GraphRAG Documentation](https://microsoft.github.io/graphrag/)

这说明：**从纯文本检索走向结构化知识组织，是当前主流演进方向之一**

但 **分面单轴漏斗路由** 和 **GraphRAG** 侧重点不同：

- **GraphRAG**：从大量文本中抽实体、关系、社区，用来回答复杂问题
- **分面单轴漏斗路由**：人工治理业务 **schema**，用来稳定做 **场景** 和 **SKU** 裁决

一个偏知识探索，一个偏业务执行

#### 9.4、小结

**最客观的判断：**

- 如果评价“学术新颖性”，**分面单轴漏斗路由** 不是最前沿概念，因为 **taxonomy**、**facet**、规则引擎、受控词表都不是新东西
- 如果评价“业务工程成熟度”，**分面单轴漏斗路由** 是很强的，因为它把 **LLM**、知识库、规则、运行时代码、业务裁决边界拆清楚了

更准确的定位是：

> **它不是 RAG 的替代品，而是 RAG 很难单独承担的业务决策层**

最佳组合应该是：

```text
RAG / LLM Wiki
-> 提供证据、事实、案例、背景材料

分面单轴漏斗路由
-> 把输入归一成 scenario / facet / SKU 决策

LLM
-> 基于裁决结果生成表达
```

在这个组合里

- **RAG / LLM Wiki** 提供证据和背景
- **分面单轴漏斗路由** 负责结构化裁决
- **LLM** 负责把裁决结果表达成用户能理解的内容

如果只用普通 **RAG**，系统可能找到了很多相关资料，但仍然不知道该选哪个 **SKU**、哪些人群不能推荐、哪个规则必须优先

如果只用**分面单轴漏斗路由**，系统可以稳定裁决，但面对大量新资料、开放问答和跨文档总结时，召回和解释能力又不够

------

因此，这套架构不是 **RAG** 的替代品，而是普通 **RAG** 很难单独承担的业务决策层

它不比 **RAG** 更普适，但在需要稳定路由、规则裁决、**SKU** 决策和合规边界的业务系统里，比普通 **RAG** 更可靠

一句话结论：

> **这套架构厉害，但厉害在工程边界和业务裁决能力，不在概念炫技；它不比 RAG 更普适，但在需要稳定路由、规则裁决和 SKU 决策的业务系统里，比普通 RAG 更可靠**

### 十、总结

当前项目的分面单轴漏斗路由架构可以压缩成三条原则：

- **单轴漏斗**：只有真正需要父子继承的 **scenario** 进入层级漏斗
- **四类元素分离**：路由主轴、平铺 `facet`、**SKU** 属性和下游消费各守边界
- **一图双向**：同一套结构正向生成，反向盘点，避免多套真值漂移

最终记忆点：

**分面单轴漏斗路由 的核心不是多建几个分类桶，而是把自然语言输入转成可判断的条件，再用“场景下钻 + facet 打标 / 横向收敛 + SKU 裁决”完成稳定路由**
