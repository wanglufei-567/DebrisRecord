## 分面模型与关系数据库：用轴描述、用谓词筛选

### 一、核心结论

**Facet** 模型、关系型数据库和维度建模共享同一个底层模型：

> 用独立的轴描述对象，再用谓词筛选对象

映射到当前知识库路由，就是：

```text
搜索词 / 关键词
  -> 模糊归一 / 别名归一
  -> scenario 场景漏斗
  -> facet 平铺打标
  -> 多条件相交收敛
  -> parent 回退 / 继承
  -> 人群硬闸
  -> SKU 裁决
  -> 下游内容消费
```

这篇资料只解决一个问题：

> 为什么人群、分型、部位、症状应作为平铺 `facet` 参与相交过滤，而不是都进入多轴嵌套树

### 二、最小概念链

| 概念 | 最小解释 | 数据库类比 |
| --- | --- | --- |
| 值 | 一个具体取值 | 单元格的值 |
| 轴 / 维度 | 一类可取值的位置 | 列 `column` |
| 组合 | 多个轴的值放在一起 | 多列组成一行 |
| 空间 | 所有可能组合构成的全集 | 各列取值的笛卡尔积 |
| 点 | 空间中的一个具体组合 | 行 `row` / 元组 `tuple` |
| 子集 | 从全集里筛出的一部分 | 查询结果集 |
| 谓词 | 判断是否留下的条件 | **WHERE** 条件 |

压缩成一句话：

> 轴定义空间，点落在空间里，谓词从空间里切出子集

### 三、数据库映射

关系型数据库可以理解为：

> 在笛卡尔积空间里，用谓词切子集

| 因果链概念 | 关系型数据库构件 | 知识库路由映射 |
| --- | --- | --- |
| 轴 / 维度 | 列 `column` | 人群、部位、分型、症状 |
| 值 | 单元格的值 | 儿童、颈部、增生、发红 |
| 点 | 行 `row` | 一个可被路由判断的对象或候选 |
| 谓词 | **WHERE** 条件 | `人群 = 儿童` |
| 复合谓词 | `AND / OR / NOT` | 多个 `facet` 相交或排除 |
| 子集 | 查询结果集 | 过滤后的候选集合 |

示例：

```sql
SELECT *
FROM candidates
WHERE audience = '儿童'
  AND scar_type = '增生';
```

这不是给对象追加描述，而是在用两个判断条件切出候选子集

### 四、三组关键区分

#### 1. 轴 / 值

轴是一类可取值的位置，值是轴上的具体取值

```text
轴：人群
值：儿童

轴：部位
值：颈部
```

把值误当成轴，会导致结构过碎
把轴误当成值，会丢失组合能力

#### 2. 正交 / 耦合

正交轴可以相对独立地组合：

```text
人群 = 儿童
部位 = 颈部
分型 = 增生
症状 = 发红
```

耦合约束不能当成普通 `facet` 扩展：

- 儿童人群不能被成人 **SKU** 兜底覆盖
- 某些 **SKU** 对特定人群、部位或阶段有禁忌
- 合规边界要求某些表述不能进入下游内容

正交轴解决组合能力，耦合约束解决业务有效性

#### 3. 组合 / 穷举

穷举式结构：

```text
术后
  -> 儿童
    -> 颈部
      -> 增生
  -> 成人
    -> 颈部
      -> 增生
```

组合式结构：

```text
scenario = 术后
人群 = 儿童
部位 = 颈部
分型 = 增生
```

组合优于穷举，因为新增维度不需要复制整棵树，运行时通过条件相交收敛候选集合

### 五、当前知识库路由映射

| 当前路由概念 | 关系数据库类比 | 工程含义 |
| --- | --- | --- |
| `facet` 平铺打标 | 给行填字段 / 贴标签 | 给对象和查询都补充可判断字段 |
| 相交收敛 | **WHERE** + `AND` | 查询侧用多个条件过滤候选集合 |
| 正交轴 | 多个可组合列 | 人群、分型、部位、症状等独立描述维度 |
| 耦合约束 | `CHECK` / 业务校验 | 人群硬闸、**SKU** 禁忌、合规边界 |
| `scenario` 漏斗 | 唯一层级主轴 | 只有场景轴承担纵向下钻和 `parent` 回退 |
| `parent` 回退 / 继承 | 从细粒度回到父层 | 子场景缺字段时继承通用场景规则 |
| **SKU** 裁决 | 最终候选选择 | 在场景和 `facet` 过滤后完成业务收口 |
| 下游内容类型 / 风格 / 标签 / 合规 | 查询结果消费者 | 消费路由结果，但不回写主轴 |

示例：

```text
搜索词：儿童甲状腺术后增生疤痕

归一：甲状腺术后 / 儿童 / 增生
scenario：甲状腺术后
facet：人群 = 儿童，分型 = 增生
过滤：scenario 命中 + 人群硬闸 + 分型条件
裁决：只允许儿童适用 SKU 进入候选
下游：内容类型、风格、标签、合规消费结果
```

### 六、与 **OLAP** 映射的关系

**OLAP** 映射解释纵向层级：

- 为什么 **scenario** 可以作为漏斗轴
- 为什么子场景可以向 `parent` 回退
- 为什么 **SKU** 裁决是漏斗收口，而不是无限下钻

**Facet** / 关系数据库映射解释横向过滤：

- 为什么人群、分型、部位、症状适合做平铺 `facet`
- 为什么多个 `facet` 可以相交收敛
- 为什么正交轴能组合，而不应全部做成嵌套树
- 为什么人群硬闸、**SKU** 禁忌和合规边界属于耦合约束

合起来就是：

```text
纵向：scenario 下钻 / parent 回退
横向：facet 打标 / 谓词过滤
收口：人群硬闸 / SKU 裁决
下游：内容类型 / 风格 / 标签 / 合规消费
```

### 七、边界与误区

重点保留四条边界：

- 谓词不是修饰词，而是可判断真假的筛选条件
- 不是所有标签都进层级树，只有同时满足 `is-a` 和 `parent` 回退的轴才进漏斗
- 正交轴不等于无约束，人群硬闸、**SKU** 禁忌、合规边界仍要单独处理
- **SQL** 只是解释模型，不代表当前项目要改成数据库建模

### 八、可复用结论

好的知识库路由不是把所有组合穷举成树，而是让 **scenario** 承担必要层级，让 `facet` 负责相交过滤，让硬闸和 **SKU** 裁决处理业务约束
