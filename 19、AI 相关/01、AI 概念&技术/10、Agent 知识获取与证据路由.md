## Agent 知识获取与证据路由

> 逻辑主线：当当前 **Context** 不足以支持任务时，**Agent** 如何识别信息缺口，找到事实责任方，选择合适的知识入口，并让经过验证的信息进入当前推理

上一篇 [《Agent 认知模型与工程架构》](<08、Agent 认知模型与工程架构.md>) 将 **Context System** 定义为 **Agent** 的核心组成之一

这带来一个更具体的问题：

> ==**Agent 需要的信息究竟从哪里来，为什么有时读取 Memory，有时搜索文件，有时使用 RAG，有时又必须查询数据库、API 或 Web**==

问题的关键不在于哪种技术更先进，而在于任务缺少什么信息、事实由谁负责，以及哪条路线能够以合适的成本提供足够可信的证据

### 一、Agent 能行动，不代表它掌握了事实

**LLM** 可以理解语言、进行推理并生成行动提议，**Tool** 可以让系统读取文件、查询服务或者改变环境

==但拥有推理能力和行动能力，不等于已经掌握完成任务所需的事实==

假设用户对差旅 **Agent** 说：

> 帮我确认下周去北京出差的住宿标准，再按我的习惯筛选酒店

这项任务至少可能依赖四类信息：

- 用户过去形成的住宿偏好
- 公司当前生效的差旅制度
- 用户当前职级、预算和审批状态
- 下周仍然可预订的酒店与实时价格

模型参数无法保证知道这些信息，当前对话也未必已经提供

即使所有信息都能被搜索到，它们的**责任方**、**时效**和**可信程度**也不一定明确：

- 用户偏好可以来自 **Memory**，但旧偏好可能已经变化
- 差旅制度可以来自文档或知识库，但命中的条款可能已经失效
- 职级与审批状态应由业务系统确认，不能从相似文本中推测
- 酒店信息需要查询当前环境，历史价格不能替代实时结果

因此，知识获取不是“给模型补充更多文字”，==而是建立一条从**信息缺口**到**可信证据**的责任链==

> ==**Agent 的知识问题，不只是能不能找到信息，而是能不能找到当前任务应该相信的信息**==

### 二、上层模型：知识如何进入一次 Agent 决策

一次完整的知识获取可以压缩成五个连续对象：

~~~text
知识来源
→ 获取方式
→ 候选信息
→ 证据
→ Context
~~~

这是本文用于识别责任边界的认知抽象，不是某个框架必须照搬的固定组件清单

![image-20260904190243813](https://raw.githubusercontent.com/wanglufei561/picture_repo/master/assets/image-20260904190243813.png)

这些对象分别回答不同问题：

| 层次 | 回答的问题 | 不能混同为 |
|---|---|---|
| **知识来源** | 信息由谁维护，谁对事实负责 | 当前保存它的物理位置 |
| **获取方式** | 系统通过什么路径接近信息 | 知识本身 |
| **候选信息** | 本次查询找到了什么 | 已经可信的事实 |
| **证据** | 哪些候选信息足以支持当前判断 | 所有检索结果 |
| **Context** | 本轮模型实际看到什么 | **Memory**、知识库或全部历史 |

**Agent / Harness** 位于这条链的控制面，负责根据任务状态选择入口、调用工具、判断是否需要补查，并将可用信息交给 **Context Builder**

模型最终消费的是本轮 **Context**，不会直接消费“整个数据库”“全部历史”或者抽象意义上的“知识库”

回到差旅任务：

~~~text
Memory 中的住宿偏好
公司制度中的有效条款
业务系统中的当前身份与审批状态
酒店服务中的实时房态
            ↓
        候选信息
            ↓
   来源、时效与任务相关性检查
            ↓
     本轮可使用的证据
            ↓
          Context
            ↓
   LLM 判断与 Agent 后续行动
~~~

这条链建立了一个重要边界：

> ==**检索只负责接近信息，验证决定能否相信，Context Assembly 决定本轮是否使用**==

### 三、知识入口没有高低，只有责任是否匹配

不同知识入口不是一条从落后到先进的升级路线

它们面对的是不同信息责任：

| 当前缺少的信息 | 优先寻找的位置 | 常见获取方式 | 首要判断 |
|---|---|---|---|
| 历史偏好、决策和经验 | **Agent Memory** | 召回、过滤 | 是否仍然有效，是否属于当前主体 |
| 明确的文件、代码和小型资料 | 本地文件或工作区 | 直接读取、**Grep**、全文搜索 | 是否存在稳定锚点，是否已经覆盖必要范围 |
| 大规模自然语言资料 | 文档库或知识库 | 关键词、语义或混合检索，必要时组成 **RAG** | 是否找到完整且可回源的证据 |
| 当前业务状态 | 数据库或业务系统 | **SQL、API、Tool** | 哪个系统拥有正式事实 |
| 最新公开信息 | 官方网站或外部环境 | **Web Search、Browser、Tool** | 来源是否权威，结果是否仍然新鲜 |

选择入口时，优先判断四件事：

- **事实责任**：哪一个主体拥有当前有效事实
- **数据形态**：信息是明确字段、精确文本，还是语义分散的自然语言
- **变化速度**：历史结论是否仍然成立，是否必须实时查询
- **任务风险**：错误信息只影响建议，还是会改变审批、资金或真实状态

例如：

- 用户的“安静、靠近地铁”偏好适合从 **Memory** 召回
- 住宿上限来自大规模制度库时可以通过 **RAG** 获取
- 用户当前职级仍应查询人事或差旅系统
- 酒店实时价格则应调用当前服务

如果只因为已经拥有向量库，就把这些信息全部交给相似度检索，技术虽然统一了，事实责任反而被抹平了

> ==**先找到事实责任方，再选择访问它的方式**==

### 四、Agent 如何形成一次信息闭环

知识获取不是一次固定搜索，而是一段受任务目标约束的信息子循环：

~~~text
发现信息不足
→ 判断缺少什么
→ 定位事实责任方
→ 选择获取路线
→ 检查候选信息
→ 装配 Context
→ 继续任务、换路、询问或停止
~~~

这里真正属于 **Agent** 的能力，不是永远选择同一种检索工具，而是根据中间结果修正路线

- 找到明确制度编号，可以从语义检索切换到精确读取
- **Memory** 与当前业务系统冲突，应让当前权威事实优先
- 搜索结果只有二手转述，可以继续寻找原始来源
- 多次补查仍不能形成充分证据，应说明不确定性或者请求用户补充信息
- 任务触及无权访问的数据，应停止而不是尝试绕过权限

停止条件同样属于知识路由

系统不是在“已经搜过一次”时停止，而是在证据已经足以支持当前任务、继续搜索的边际价值过低，或者权限、时间和成本边界已经到达时停止

这一子循环最终仍服务于完整 **Agent Loop**；关于任务如何持续推进、验收和结束，由后续 [《Loop Engineering 相关》](<13、Loop Engineering 相关.md>) 继续展开

### 五、Memory、RAG、Tool 与 Context 的边界

这些概念经常同时出现在知识获取链中，但承担的责任不同：

| 概念 | 主要对象 | 核心责任 |
|---|---|---|
| **Memory** | 历史状态、偏好、决策与经验 | 决定什么值得保存、召回、更新和遗忘 |
| **RAG** | 外部资料及其检索结果 | 让与问题相关的资料作为证据参与生成 |
| **Tool** | 文件、数据库、服务与环境能力 | 为 **Agent** 提供读取或行动入口 |
| **Context** | 本次模型调用的实际输入 | 在有限预算内组织当前任务所需信息 |
| **Agent / Harness** | 任务状态与控制过程 | 选择路线、调用工具、验证结果并决定下一步 |

相对 **LLM** 参数和当前输入，**Memory** 与外部检索都在提供原本不可见的信息

但相对完整 **Agent** 系统：

- **Memory** 是系统主动维护、准备未来复用的信息
- 外部知识仍由文件、知识库、数据库、业务服务或互联网来源负责

两者可以共享关键词检索、向量检索或重排等技术，但不共享治理责任

同样，**Grep** 与 **RAG** 也不是严格的同层概念：

- **Grep** 是一种精确匹配的访问工具
- 语义检索是一类按含义寻找候选信息的机制
- **RAG** 是让检索结果进入生成过程的系统模式，底层可以组合精确、关键词、向量或其他检索方式

### 六、工程判断：不存在统一最优的知识入口

知识获取系统的成熟度，不取决于接入了多少检索技术，而取决于路线复杂度是否与任务需要相称

- 少量且稳定的资料能够直接进入 **Context**，不必先建设索引
- 存在精确名称、错误码或代码符号时，直接读取和词法搜索通常更可解释
- 资料规模大、表达差异明显并且查询持续重复时，索引检索与 **RAG** 才更可能值得投入
- 当前业务事实已经由数据库或服务维护时，应查询权威系统，而不是从文本中重新推测
- 来源冲突、时效敏感或行动后果较高时，需要提高验证和人工检查强度

更复杂的路线能够扩大信息覆盖，也会增加同步、权限、延迟、成本和错误归因负担

因此，工程选择不是从 **Grep** 升级到向量检索，再升级到 **Agentic RAG**，而是为当前信息缺口选择最窄、足够、可验证的路线

> ==**路线应随事实变化，不应随技术热度变化**==

### 七、最终认知模型

整篇文章可以收束为三层判断：

~~~text
来源层：事实由谁负责
获取层：Agent 怎样接近事实
使用层：什么能够进入当前 Context
~~~

三者之间不能跳步：

- 找到信息，不代表找到了权威来源
- 命中候选，不代表形成了充分证据
- 进入 **Context**，不代表模型一定会正确使用
- 模型给出结论，不代表真实环境已经发生变化

最终只需要记住：

> ==**先找事实责任方，再选获取方式；先验证候选信息，再装配当前 Context**==

### 八、复习问题

1. 为什么 **Agent** 能够调用工具，并不等于它已经掌握完成任务所需的事实
2. 知识来源、获取方式、候选信息、证据与当前 **Context** 分别回答什么问题，为什么不能混用
3. 为什么知识获取应当先确定事实责任方，再选择获取方式
4. 当 **Agent** 缺少历史偏好、明确代码事实、大规模自然语言资料、当前业务状态和最新公开信息时，分别应该优先访问什么来源
5. **Memory、RAG、Tool、Context** 与 **Agent / Harness** 在知识获取链中分别承担什么责任
6. 为什么 **Grep**、语义检索与 **RAG** 不能被简单看作同一层级的三种检索工具
7. 信息被检索出来后，为什么不能直接、完整地进入当前 **Context**
8. 当候选信息相互冲突、证据持续不足或任务触及访问权限边界时，**Agent** 应当如何处理

### 九、复习问题参考答案

1. **行动能力与事实能力**：工具只为 **Agent** 提供访问或改变环境的入口，并不保证信息已经被获取、来源权威、内容有效或足以支持当前判断；事实仍需经过定位、获取和验证

2. **知识进入决策的五个对象**

   - 知识来源回答事实由谁维护和负责
   - 获取方式回答系统怎样接近信息
   - 候选信息是本次查询找到的内容
   - 证据是足以支持当前判断的候选信息
   - **Context** 是本轮模型实际看到的信息

3. **事实责任优先**：访问方式只能决定如何取得信息，不能决定哪一份信息拥有最终解释权；先确认事实责任方，才能避免用方便检索的副本替代当前有效事实

4. **信息缺口与优先来源**

   - 历史偏好优先从 **Agent Memory** 召回，并检查主体与时效
   - 明确代码事实优先直接读取文件，配合 **Grep** 或全文搜索
   - 大规模自然语言资料优先访问文档库或知识库，必要时使用 **RAG**
   - 当前业务状态优先查询拥有正式事实的数据库、业务系统或 **API**
   - 最新公开信息优先查询权威官方网站或当前外部环境

5. **各概念的责任边界**：**Memory** 管理值得跨任务保存和复用的信息，**RAG** 让外部资料参与生成，**Tool** 提供访问与行动入口，**Context** 组织本轮模型输入，**Agent / Harness** 负责选路、调用、验证与推进任务

6. **访问机制与系统模式**：
   - **Grep** 是精确匹配工具，语义检索是按含义寻找候选信息的机制

   - **RAG** 是将检索结果用于生成的系统模式；**RAG** 的底层可以组合精确、关键词、向量等多种检索方式

7. **从候选信息到 Context**：
   - 检索结果仍需检查来源、时效、主体归属、任务相关性和冲突情况

   - 只有能够支持当前判断的部分才形成证据，并由 **Context Assembly** 按相关性与预算装配，而不是把全部结果直接塞给模型

8. **冲突、不足与权限边界**：来源冲突时应回到事实责任方并提高验证强度，证据不足时应换路补查、保留不确定性或请求用户补充，触及权限边界时应停止并交还控制权，不能绕过权限继续获取
