## 用专家工作模式约束 Agent：从能力清单到可执行上下文

### 一、能力清单为什么不够

先看一个教学示例：

> 用户要求：“基于最近客户反馈，规划下周 5 条 **LinkedIn** 内容”

此时，**Agent** 可能已经具备分析反馈、生成选题、查询知识库、保存草稿和质量复核等能力

但能力存在，不代表它们已经被组织成一次正确的业务执行

**Agent** 仍然需要判断：

- 当前任务应从什么业务角色出发
- 服务哪个业务主体，使用哪些知识
- 应优先组合哪些 **Skill** 和 **Tool**
- 证据、草稿和审核结果分别放在哪里
- 什么时候需要交接或复核

如果这些问题没有明确答案，**Agent** 即使拥有全部能力，也可能使用错误的品牌知识、把个别反馈当成普遍结论，或者绕过审核直接生成对外内容

专家工作模式解决的正是这个缺口：把一类业务任务需要的场景、身份、知识、能力、数据和交付边界组织成专家上下文

**==能力清单回答“能做什么”，专家工作模式回答“这次按什么上下文做”==**

### 二、专家工作模式是什么

一个**「专家工作模式」**描述的是**一类任务共享的工作上下文**，例如：

- `content-strategist`：内容策略专家模式
- `customer-support`：客户支持专家模式
- `research-analyst`：研究分析专家模式

它不等于一次具体任务，也不等于一个新的 **Agent**

- 同一个 **Agent** 可以根据任务进入不同模式，一个编排器也可以把不同子任务交给采用不同模式的 **Agent**


它也不等于 **Workflow**

- 专家工作模式限定当前任务的工作上下文
- **Workflow** 规定相对明确的执行步骤或代码路径
- **Agent** 在上下文和运行时边界内判断下一步行动

因此，步骤和分支完全确定的任务可以直接使用代码化 **Workflow**；目标明确但路径依赖语义判断的半结构化任务，更适合使用专家工作模式

一次任务的逻辑位置如下：

```text
用户任务
  -> Agent 或编排器选择专家工作模式
  -> 装配角色、领域、知识范围和工作规则
  -> Agent 选择 Skill
  -> Tool 执行检索、读取、写入或外部调用
  -> 交接规则或质量门决定能否继续交付
```

专家工作模式可以由 **Markdown**、**YAML**、**JSON** 或代码配置承载，但文件格式不是模式本身

只有当它实际影响模式选择、上下文装配、能力使用、数据范围和交付条件时，它才进入了运行时

**==模式定上下文，Skill 给流程，Tool 供能力，Runtime 守边界==**

### 三、专家工作模式包含什么

专家工作模式保留八个组成部分，它们分别回答一次任务中的不同问题：

| 组成部分 | 回答的问题 | 不能替代什么 |
|---|---|---|
| 工作场景 | 承接哪一类业务问题 | 不代表本次任务已经命中 |
| 身份契约 | 采用什么角色、租户、领域和知识范围 | 不替代认证、授权和权限隔离 |
| 触发意图 | 什么用户目标会进入该模式 | 不只是关键词匹配 |
| 声明技能 | 通常优先组合哪些 **Skill** | 不是封闭白名单或固定流程 |
| 工具边界 | 可以使用哪些 **Tool**，各自提供什么能力 | 不把隐蔽业务判断塞进工具 |
| 数据面 | 证据、知识、草稿、状态和审核结果放在哪里 | 文件路径不等于事实责任 |
| 交接规则 | 什么情况下转给其他模式或流程 | 不只是切换模式名称，还要传递状态 |
| 质量门 | 哪些产物必须复核后才能交付 | 声明质量门不等于已经执行检查 |

八个部分并不是八个彼此独立的模块

- 工作场景与触发意图决定为什么进入
- 身份契约限定如何理解任务
- 声明技能、工具边界和数据面支撑执行
- 交接规则与质量门控制任务如何退出

其中最容易混淆的边界是：

> 专家工作模式提供专家上下文，**Skill** 提供具体操作流程

**Tool** 可以提供数据、动作或外部服务能力，但其输入、输出和副作用应当清晰可观察

由 **Agent** 判断为什么调用工具，由工具执行明确能力，由运行时检查权限和不可逆操作

### 四、Soft Harness 与 Hard Harness

**Harness** 是包裹模型并支撑 **Agent** 运行的工程系统，包括上下文、工具、状态、执行循环、验证和安全边界

本文使用 **Soft Harness** 和 **Hard Harness** 区分两种约束方式

**Soft Harness** 通过模型能够理解的文本和结构化信息引导行为，例如：

- 专家工作模式
- 触发意图和工具说明
- 交接规则和质量要求
- “证据不足时不要给出确定性判断”这类语义规则

**Hard Harness** 通过代码和运行时机制强制执行边界，例如：

- 状态机和 **Schema** 校验
- 租户与数据访问权限
- 写操作确认和审批流
- 自动化测试、评测和审计

两者不是先后替代关系

需求尚未稳定时，可以先用 **Soft Harness** 表达语义规则；但权限隔离、敏感操作和强合规要求从一开始就应由 **Hard Harness** 约束

**==Soft Harness 引导应该怎样做，Hard Harness 保证哪些边界不能突破==**

### 五、完整任务如何运行

继续使用开头的教学示例，它用于说明逻辑关系，不表示某个现有系统已经实现了这些配置

用户提出：

> “基于最近客户反馈，规划下周 5 条 **LinkedIn** 内容”

任务依次发生以下变化：

1. **Agent** 或编排器根据目标产物和证据类型，选择 `content-strategist` 模式
2. 模式提供当前品牌、内容领域、知识范围和工作规则
3. 运行时检查当前用户是否有权读取对应客户反馈
4. **Agent** 选择反馈分析和内容策划类 **Skill**
5. **Tool** 读取客户反馈和品牌事实，并把内容计划保存为待审核草稿
6. 如果反馈数量不足，按照交接规则补充研究或标记证据限制
7. 因为产物将对外发布，质量门检查事实依据、客户信息和产品承诺
8. 只有质量门通过且运行时允许写入正式内容日历，任务才进入可交付状态

这条链路说明，专家工作模式不是替代 **Agent** 推理，而是让推理发生在明确的业务上下文和工程边界内

它适合以下情况：

- 同一套 **Agent** 能力服务多个领域、业务主体或输出场景
- 一类任务需要组合多个 **Skill**、**Tool** 和知识范围
- 任务目标相对稳定，但完成路径仍依赖语义判断
- 任务存在明确的数据责任、交接和质量要求

以下情况不应优先使用专家工作模式：

- 一个简单 **Skill** 就能完成的单点任务
- 步骤完全确定、适合代码化 **Workflow** 的任务
- 只有“专家角色”包装，没有真实业务边界的任务
- 需要严格权限或合规控制，却只有文本规则的任务

最终需要记住的不是模式配置里有多少字段，而是它承担的组织责任：

> 面对一类业务任务，专家工作模式先限定工作上下文，再组织 **Skill**、**Tool**、数据、交接和质量门
