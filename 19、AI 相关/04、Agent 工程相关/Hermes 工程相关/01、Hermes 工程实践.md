**核心结论**

单独维护一个 `kb` 是合理的，但前提是它不能只是“文档仓库”

它应该定位成：

```
KB = 业务真值层 + 运行时契约层 + Agent 可读上下文层
profile = 执行层 / 工具层 / 运行时实现层
```

如果 `kb` 只有概念、说明、契约，而没有和 `profile` 实现机制之间的映射文档、自测和消费边界，那确实会产生你说的“认知链路脱节”

**一、KB 的目标消费方不是单一对象**

它不是只给人看的，也不是只给 **Agent** 看的，更不是只给代码读的

准确说，它有三类消费者：

| 消费方          | 消费什么                         | 举例                                                         |
| --------------- | -------------------------------- | ------------------------------------------------------------ |
| 人类            | 架构边界、维护规则、业务判断依据 | 看 `README`、`index.md`、契约文档                            |
| **Agent / LLM** | 语义内容、规则说明、写作上下文   | 读取场景正文、SKU 事实卡、合规规则                           |
| 程序代码        | 结构化字段、生成物、路径约定     | 读取 `taxonomies.json`、SKU frontmatter、`route_decision.json` |

所以 `kb` 的定位不是“给谁看”，而是：

```
把业务真值整理成能被人维护、被 Agent 理解、被代码稳定消费的形态
```

**二、契约本身确实不能落地**

你说得对，`contracts` 只是定义约束

例如 `RouteDecision` 契约只能说明：

```
这个对象应该长什么样
哪些字段最小必填
哪些字段是审计扩展
它不是什么
```

但它不能自己生成 `route_decision.json`

真正落地要靠 profile 里的实现：

```
kb_router.py
-> choose_recipe()
-> build_route_decision()
-> write_outputs()
-> route_decision.json
```

所以完整闭环应该是三层：

```
契约层：对象应该是什么
机制层：对象如何产生、何时落盘、谁引用
实现层：当前代码在哪个函数里做这件事
```

现在缺的正是中间这层“机制层”

**三、所以单独维护 KB 是否僵硬，取决于有没有桥**

如果只有：

```
kb 写契约
profile 自己写代码
两边靠人脑记忆对应
```

那就很僵硬，也容易漂移

但如果形成下面这种关系，它就是合理的：

```
kb 定义真值和契约
profile 只实现消费和执行
机制文档说明两者如何连接
自测保证实现没有偏离契约
```

也就是：

```
KB 不是实现代码的替代品
KB 是实现代码必须遵守的业务真值和对象协议
```

**四、当前最应该补的桥**

我建议继续沿用你刚认可的结构：

```
routing_decision/contracts/
-> route_decision_contract.md
-> route_decision_runtime.md
```

其中：

- `route_decision_contract.md` 说明对象长什么样
- `route_decision_runtime.md` 说明对象怎么从 `kb_router.py`、`choose_recipe()`、`build_route_decision()` 到 `route_decision.json`
- profile 代码只是实现细节，不把业务认知藏在代码里

这样读者的认知链路就闭合了：

```
我知道 RouteDecision 是什么
我知道它为什么存在
我知道它由谁生成
我知道它在哪里落盘
我知道谁消费它
我知道当前实现在哪个脚本里
```

**五、一句话收束**

你现在的困惑不是“KB 是否应该独立存在”，而是“KB 和 profile 之间缺少运行时机制桥”

所以我的判断是：

```
KB 单独维护是合理的，但必须把契约、运行机制、实现入口和验证方式连起来；否则它就会退化成一套漂亮但悬空的说明文档
```
